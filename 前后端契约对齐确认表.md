# 前后端契约对齐确认表 · PadGuard 服务端建设前

> 用途：服务端开发前，与「护航控制端（家长端）」「护航成长（被管控端/孩子端）」两端开发对齐契约冲突。  
> 用法：**「建议默认方案」视为提案**，无异议请直接采纳；有异议在「最终决定」列填写，双方确认后服务端据此实现。  
> 版本：V1.0 ｜ 2026-09-14

---

## 一、总体结论（先对齐认知）

1. **必须建设独立服务端**，它是连接家长端与孩子端的唯一桥梁。
2. 服务端同时暴露**两套入口**：
   - 控制端（家长）：REST `https://<域名>/v1/` + WebSocket `wss://<域名>/ws`
   - 被管控端（孩子）：REST `https://<域名>/api/v1` + MQTT（EMQX `8883`）
3. 当前两端均"契约就绪、未连真服务"：控制端用 `LocalDataSource` Mock，孩子端绑定用演示码 `123456` Mock。**对齐后两端需同步"接真线"**（见教程 §8）。

## 二、核心冲突确认表（必对齐，9 项）

| # | 议题                  | 控制端（家长）现状                                        | 被管控端（孩子）现状                                                                   | 冲突点                                            | 建议默认方案                                                                                                                                                                                                   | 最终决定 | 状态 |
| - | ------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -- |
| 1 | **API Base URL 前缀** | `/v1/`（如 `/v1/devices`）                          | `/api/v1`（如 `/api/v1/device/bind`）                                           | 前缀不一致，服务端若只接一套则另一端调不通                          | 服务端**两套前缀都实现**（同一网关下分两组路由）；后续重构再统一                                                                                                                                                                       |      | ⬜  |
| 2 | **域名**              | `api.padguard.com`                               | `api.padguard.cn`                                                            | `.com` 与 `.cn` 不同                              | 统一为 **`api.padguard.cn`**（国内合规/备案更稳）；测试环境用 `test-api.padguard.cn`                                                                                                                                        |      | ⬜  |
| 3 | **统一响应包装字段**        | `{code,message,data,timestamp}`                  | `{code,message,data,serverTime}`                                             | 时间戳字段名不同（`timestamp` vs `serverTime`）          | 服务端按**调用方路由**返回对应字段名；长期统一为 `serverTime`                                                                                                                                                                  |      | ⬜  |
| 4 | **错误码体系**           | `0/1001/1002/1003/2001/2002/2003/3001/3002/5001` | `0/40001/40101/40301/40302/40303/40901/50000`                                | 两套码段、语义不同                                      | 按**调用方路由分流**：控制端走 1xxx/2xxx/3xxx，被管控端走 40xxx；长期统一一套（推荐被管控端码段，信息更细）                                                                                                                                       |      | ⬜  |
| 5 | **绑定流程与接口**         | `POST /devices/bind {deviceId, alias}`           | `POST /device/bind {bindCode, deviceSn, fingerprint, model, controlMode, …}` | 控制端用"已知 deviceId 绑定"，孩子端用"bindCode 反向注册"，流程对不上 | **以孩子端契约为准**：① 家长端生成 6 位一次性 `bindCode`（10 分钟有效）→ ② 孩子端 `POST /device/bind` 上报 → ③ 服务端下发 `deviceId`+`deviceToken`+MQTT 凭据+`hmacSecret` → ④ 服务端绑定到该家长并推"设备已绑定"事件。控制端 `/devices/bind` 接口**废弃或改为"查询待绑定码状态"** |      | ⬜  |
| 6 | **设备唯一标识 deviceId** | 展示用 `id`/`deviceId`（如 `PAD_XIAOMI_001`）          | 服务端下发的 UUID（全局主键，如 `d7f3a1c2-…`）                                             | 标识生成方与格式不同                                     | 统一用**服务端下发的 UUID** 作为 `deviceId` 全局主键；家长端展示的 `id` 直接等于该 UUID，不再自造可读 ID                                                                                                                                   |      | ⬜  |
| 7 | **控制模式枚举语义**        | `NORMAL / LEARNING / FOCUS`（使用场景模式）              | `DEVICE_OWNER / PROFILE_OWNER / DEVICE_ADMIN / LEGACY`（系统权限等级）               | 同名"模式"但语义不同，易互相覆盖                              | **两个独立字段分别存储**：`sceneMode`（家长设定场景）+ `controlMode`（孩子端上报权限等级），互不直接覆盖                                                                                                                                      |      | ⬜  |
| 8 | **令牌有效期与刷新**        | 家长 JWT：access + refresh（refresh 头传递）             | 设备 `deviceToken`：契约建议 30 天 + refresh（§10 待确认项 3）                             | 设备端是否给 refresh、有效期多久未定                         | 家长端 access 2h + refresh 30d；设备端 `deviceToken` 30d + `refreshToken` 30d，绑定响应一并返回                                                                                                                          |      | ⬜  |
| 9 | **策略分组下发粒度**        | 无显式分组下发，按 `/policies/{deviceId}`                 | 一设备一策略；按班级分组下发由服务端展开（§10 待确认项 4）                                             | 是否支持"分组批量下发策略/指令"                              | MVP 阶段**一设备一策略**；分组（班级）在服务端展开为"逐设备下发"，指令支持 `broadcast/{groupId}` topic（孩子端已定义）                                                                                                                           |      | ⬜  |

## 三、绑定流程图（对齐后）

```
家长端                              服务端                              孩子端
  │                                   │                                  │
  │ 1.生成绑定码(6位,10min)            │                                  │
  │─────────── POST /devices/bind-code ──▶ 存 Redis(bindCode→user_id)    │
  │                                   │                                  │
  │ 2.展示二维码/数字码               │                                  │
  │                                   │           3.扫码/输入 bindCode     │
  │                                   │◀── POST /device/bind ─────────────│
  │                                   │   {bindCode,deviceSn,fingerprint, │
  │                                   │    model,controlMode,...}         │
  │                                   │                                  │
  │                                   │ 4.校验码有效 → 生成 deviceId(UUID) │
  │                                   │   签发 deviceToken+mqtt凭据+      │
  │                                   │   hmacSecret → 落 devices+绑定关系 │
  │                                   │──────── 返回令牌结构 ─────────────▶│
  │                                   │   {deviceId,deviceToken,          │
  │                                   │    mqttUsername,mqttPassword,     │
  │                                   │    hmacSecret,expiresAt}          │
  │                                   │                                  │
  │ 5.收到"设备已绑定/上线"事件(WS)    │                                  │
  │◀──── device.online / bound ───────│                                  │
  │ 6.GET /devices 即见新设备         │                                  │
```

> 注：第 1 步"生成绑定码"接口当前控制端契约未定义（`/devices/bind` 是反向绑定），需**新增** `POST /devices/bind-code`，见冲突 #5。

## 四、被管控端契约 §10 待确认项（原文 8 项 + 建议答复）

| # | 待确认项                       | 建议默认答复                                                                                            |
| - | -------------------------- | ------------------------------------------------------------------------------------------------- |
| 1 | MQTT Broker 部署方案与域名        | **EMQX**（Docker 部署），域名 `mqtt.padguard.cn:8883`；测试 `tcp://test-mqtt.padguard.cn:1883`              |
| 2 | 租户隔离 `tenantId` 是否纳入 topic | **单租户初期省略** `tenantId`（topic 用 `pg/v1/down/{deviceId}/...`）；预留占位，后续多租户再启用                         |
| 3 | `deviceToken` 有效期与刷新接口     | 30 天 + refresh（见冲突 #8）                                                                            |
| 4 | 策略是否支持按班级分组下发              | MVP 一设备一策略，分组在服务端展开（见冲突 #9）                                                                       |
| 5 | 截图存储：直传 OSS 还是经服务端中转       | **预签名 URL 直传 OSS/MinIO**，服务端只存元数据 URL（防大文件中转）                                                     |
| 6 | 是否 mTLS 加固 MQTT            | 初期**单向 TLS + 账号密码**；高安全场景再加 mTLS                                                                  |
| 7 | 临时解锁闭环（§9）服务端实现            | 服务端落 `unlock_requests` 工单、审批后下发 `TEMP_UNLOCK`（带 `packageName`）、拒绝下发 `SHOW_MESSAGE`（带 `requestId`） |
| 8 | `POST /device/bind` 真实联调   | 孩子端移除 `123456` Mock，改调真实 `POST /device/bind`（见教程 §8）                                              |
