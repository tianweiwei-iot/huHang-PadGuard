## 三、修复计划与改动位置

### 3.1 G-01：退款即回收会员权益

**决策**：经产品拍板采用「退款即回收」策略（用户选择项）。原 `AdminBillingService.refund` 注释为「订阅权益不自动回收（显性设计约定）」，属历史刻意选择，故先确认再落地。

**实现**：在 `BillingService` 新增 `@Transactional revokeRightsOnRefund(userId)`：
- 取该家长订阅（`findByUserId`，订阅按 `user_id` 唯一）；
- 仅对 `ACTIVE` / `TRIAL` 生效，已 `EXPIRED` / `REVOKED` 直接跳过（幂等）；
- 置 `status = REVOKED`、`expiredAt = now`、`updatedAt = now` 并 save；
- `SubStatus.REVOKED` 在 `ensureActive` / `statusOf` 中按「无权益」处理（与 EXPIRED 同效），即退款即停服。

**两处退款路径统一调用**：
1. `BillingService.handleWeChatRefundNotify`（微信退款回调二次确认后）；
2. `AdminBillingService.refund`（后台手动退款受理后）。

- 位置：`service/BillingService.kt`、`service/AdminBillingService.kt`
- 覆盖：微信回调退款 + 后台手动退款两条路径，避免「手动退了还留权益」的遗漏。
- 测试：`BillingServiceTest` 新增 2 例（ACTIVE→REVOKED 且幂等；已过期/无订阅安全 no-op）。

### 3.2 G-02：解绑清除 retained MQTT 消息

**根因**：`DeviceService.unbind` 清理了 DB 业务数据并推送 unbind 指令，但策略通知以 `retained=true` 形式下发（`MqttGateway.publishPolicyNotify`），解绑后该 retained 仍留在 Broker；同一台平板被新家长重绑/他人捡到绑定，上线即拉到旧 retained 策略，导致「解绑后旧策略仍生效 / 新家长策略被覆盖」。

**实现**：`MqttGateway` 新增 `clearRetained(deviceId)`（向策略/配置下行主题各发一条空 `retained=true` 消息顶掉旧 retained）；`DeviceService.unbind` 在清数据后调用，失败仅 warn 不阻断主流程。
- 位置：`mqtt/MqttGateway.kt`、`service/DeviceService.kt`
