# 孩子端守护自愈与玻璃球悬浮框 · 顶层设计与实施方案

> 版本：v1.0 ｜ 日期：2026-10-20 ｜ 范围：孩子端（护航成长）为主，家长端/服务端仅做契约核对
> 保密级别：内部文档，仅存本地仓库，不得外发。

---

## 一、需求还原与现象拆解

### 1.1 需求 1：自启动守护功能未生效

现场现象（分解为三个可独立验证的事实）：

| # | 现象 | 推断根因 | 验证方式 |
|---|---|---|---|
| A | 安装配置后管控应用能运行（基础链路 OK） | — | 已确认 |
| B | 孩子端（管控应用）UI 出现在「最近任务」历史记录里 | `MainActivity` 未声明 `excludeFromRecents`，绑定隐藏后任务卡仍驻留 | 查 Manifest：MainActivity 无该属性 |
| C | 划掉孩子端任务后，进程退出、**守护不自动重启**，屏幕监控授权消失，需手动打开孩子端并重新授权 | 进程被杀后缺少可靠的自愈通道：`onTaskRemoved` 的延迟重启在"进程当场被杀"时失效；`START_STICKY` 无时限保证；`GuardWatchdogService`（JobScheduler 60~90s）是唯一外部通道，Android 12+ 上从 Job 回调启动前台服务可能被系统拒绝（代码仅记日志降级），且部分 ROM 会限制 JobScheduler 投递 | 读 GuardService/GuardWatchdogService/BootReceiver 源码 |
| D | 屏幕监控授权（MediaProjection 令牌）随进程死亡消失 | MediaProjection 令牌是**进程内 IBinder**，Android 隐私红线决定其无法持久化；正确出路是"无障碍截屏通道（持久授权）+ 看屏会话自愈"，而非试图保存令牌 | 读 ScreenCaptureSession/AccessibilityScreenshot/AccessibilityLiveStreamer |

**结论**：需求 1 的根因不是"没写守护代码"，而是**进程级保活的最后一公里不可靠**（划任务=杀进程时，恢复依赖单点 JobScheduler，时效与成功率都没有保证），叠加**看屏链路缺少进程重启后的主动恢复**（只能被动等服务端重发指令，服务端重发有 8s 冷却 + 依赖家长端仍在观看）。

### 1.2 需求 2：悬浮框重设计为「玻璃球」

现状：`FloatingStatusController` 是一张 WindowManager 纯文本卡片（标题+已用+剩余），无拖拽、无进度可视化、延时申请入口只存在于孩子端 App 内的 Compose 浮层（`UsageSessionHost`）——**而孩子端绑定后图标已隐藏，孩子平时根本看不到那个入口**。延时申请三端链路（工单审批）已完备，缺的只是一个"孩子日常可见可操作"的载体。

目标形态：
- 炫酷玻璃球，浮于应用最顶层，可拖拽移动、松手吸附边缘、位置记忆；
- 球面显示**已使用时长**与**剩余使用时长**（秒级刷新，与服务端基线同源）；
- **双击**玻璃球 → 弹出「申请延时」对话框 → 选档提交工单 → 家长确认 → 时间生效，各端完全同步。

## 二、顶层设计

### 2.1 守护自愈架构（四层保活 + 双进程互保）

```
                 ┌────────────────────────────────────────────┐
                 │              系统侧调度通道                  │
                 │                                            │
   ①BootReceiver │ 开机/覆盖安装/QUICKBOOT/USER_PRESENT        │
   ②onTaskRemoved│ 任务被划掉且进程尚在（秒级）                 │
   ③START_STICKY │ 系统尽力重建（无时限保证）                   │
   ④JobScheduler │ GuardWatchdogService 一次性任务 60~90s       │
   ⑤AlarmManager │ GuardAlarmReceiver 60s 窗口闹钟（新增）      │
                 └────────────────────────────────────────────┘
                 ┌────────────────────────────────────────────┐
                 │           应用侧双进程互保（新增）            │
                 │                                            │
                 │  主进程 :app         守护进程 :daemon        │
                 │  GuardService   ←→   GuardDaemonService     │
                 │  每15s写心跳文件      每5s检查双方心跳        │
                 │  (guard_alive)        (daemon_alive)        │
                 │       │ 心跳超时45s即拉起对方                 │
                 │       ▼                                     │
                 │  guard_state 文件记录"是否已绑定"             │
                 │  （未绑定 → daemon 不起服务并自停，防止解绑后  │
                 │    反复重启打扰）                            │
                 └────────────────────────────────────────────┘
```

**关键设计决策：**

1. **文件心跳而非 SharedPreferences**：SharedPreferences 实例按进程缓存，跨进程写入不会推送到另一进程的实例，读取会拿到陈旧值。心跳改用「写临时文件 → rename 原子替换」，跨进程读取必然拿到最新值。
2. **守护进程只做「拉活」不做「管控」**：`:daemon` 进程极轻（无 Hilt、无数据库），唯一职责是心跳检查与拉起主进程，自身由 START_STICKY + 开机广播 + 看门狗 + 闹钟共同保活。主进程死亡时它能在 **≤45s** 内把 GuardService 拉回（15s 心跳间隔 + 45s 超时阈值可在常量中调整）。
3. **绑定态门控**：`guard_state` 文件由 GuardService 在绑定态变化时写。未绑定设备 daemon 发现心跳陈旧时**不拉服务**（没有家长就没有管控依据，与 GuardService 现有 `boundNow` 语义一致），并自停避免空转。
4. **看屏会话主动恢复**：`LIVE_VIEW_START` 生效时把「高清档位 + 截止时间」写入 `live_view_state` 文件；进程重启后 bootstrap 检查该窗口仍然有效且无障碍通道可用 → **立即主动恢复推流**，不等服务端重发（服务端 `reconcileLiveSessions` 8s 冷却重发作第二保险）。
5. **最近任务隐藏**：`MainActivity` 声明 `android:excludeFromRecents="true"`，孩子端任务不再出现在历史记录（现象 B 直接消除；其余管控页早已 excludeFromRecents）。

**边界如实声明**：被系统「设置 → 强制停止」进入停止态后，所有应用层通道（含双进程）均失效——这是 Android 安全模型，唯一正解是 Device Owner（`SecurityEnforcer.DISALLOW_APPS_CONTROL` 置灰停止按钮）。该边界写入交付文档，不谎称可绕过。

### 2.2 玻璃球悬浮框设计

```
        ╭──────────────╮
        │   已用 45分   │  ← 球面上排（小字，9sp）
        │  ┌────────┐  │
        │  │  30:00 │  │  ← 球体中心：剩余时间大字（mm:ss，<60min）/ 分钟（≥60min）
        │  └────────┘  │
        │   剩余 30分   │  ← 球面下排（小字）
        ╰──────────────╯
        外圈进度环：剩余比例（>50% 青 → 20~50% 琥珀 → <20% 红）
        待审核态：环呼吸闪烁 + 中心显示「待审 +15分」
```

- **绘制**：自定义 `GlassBallView`（Canvas）：`RadialGradient` 玻璃体 + 左上高光 + 底部反光 + `drawArc` 进度环 + 两行文字。不引入 ComposeView（避免 overlay 窗口里的 Compose 生命周期与重组开销），纯代码绘制，性能与可控性最佳。
- **交互**（`onTouchEvent` + `GestureDetector`）：
  - **拖拽**：位移超 8dp 进入拖拽，实时 `updateViewLayout` 跟随；松手 `ValueAnimator` 吸附最近屏幕边缘（左右），位置按百分比持久化（`glassball_pos` prefs，按当前屏幕尺寸校验，旋转/分辨率变化不丢）。
  - **单击**：保留既有能力——唤起家长验证入口（`FloatingActionActivity`），这是隐藏形态下家长唯一的触点，不能因重设计丢失。
  - **双击**：弹出 `GlassBallDialogActivity`（透明主题 Compose 对话框）申请延时。
- **数据源**（与锁机判定、家长端头条同源，杜绝"球上剩 10 分钟、设备却已锁"）：
  - 会话激活：`UsageSessionManager.liveRemainingMs(校准墙钟)` 秒级插值；额度 = `quotaMinutes + extendedMinutes`（含已批准延时）；
  - 会话未激活：回退本地策略额度 − UsageStats（与 `UsageStatusProvider` 同算法）；
  - 待审核：`pendingDelayMinutes > 0` → 球进入待审态，对话框档位置灰只读。
- **可见性**：绑定后展示、解绑/暂停管控时隐藏（复用 GuardService `observeBinding` 驱动）；缺 `SYSTEM_ALERT_WINDOW` 权限时静默不展示（与现卡片一致，不抛异常）。

### 2.3 延时申请与三端同步（复用既有审批流，零服务端改动）

```
孩子双击玻璃球 → GlassBallDialogActivity
   → UsageSessionManager.requestDelay(minutes)
   → POST /usage/session/delay/request            （孩子端 → 服务端，仅建 PENDING 工单）
   → 服务端 UsageDelayService.request             （单设备单 PENDING + 单日≤120 校验 + WS 推送家长）
   → 家长端：消息中心铃铛红点 + 全局弹窗 / 时间管控页内联审批（已实现）
   → 家长点「同意」→ UsageDelayService.approve    （session.extendedMinutes += minutes，WS 通知家长端刷新）
   → 孩子端 15s 会话轮询带回新 extendedMinutes    → liveRemainingMs 立即变大
   → 玻璃球剩余数字秒级更新；锁机判定（PolicyEngine.tick）同步解除
```

- **防绕过**：待审核期间对话框只读、服务端单 PENDING、单日上限三保险（已实现，本次不改动）。
- **拒绝路径**：家长拒绝 → 服务端下发 `SHOW_MESSAGE` → 孩子端消息页弹出「申请未通过」（已实现）。
- **时间完全同步的锚点**：服务端 `startEpoch + serverNow` 权威基线；孩子端本地只做插值；家长端展示同一基线。三方都不会因改本地时间漂移。

## 四、验收清单（真机）

**守护自愈**
1. 绑定后打开孩子端（或任意入口使其进程起来）→ 划掉最近任务中的孩子端卡片 → **≤90s 内**心跳恢复、家长端设备回到在线；
2. `adb shell am kill com.padguard.child.debug`（SIGKILL）→ 同样 ≤90s 自愈；
3. 重启平板 → 开机自启后守护在、看屏可恢复；
4. 解绑 → daemon 自停，不再反复重启打扰。

**玻璃球**
5. 绑定后玻璃球常驻最顶层，跨应用可见；
6. 拖拽移动松手吸附边缘；杀进程后位置保持；
7. 已用/剩余秒级刷新，与锁机判定、家长端看板一致；
8. 双击 → 选档提交 → 家长端弹窗/铃铛收到 → 同意后玻璃球剩余立即增加、三端一致；
9. 待审核期间球体待审态、对话框只读；
10. 无 SYSTEM_ALERT_WINDOW 权限时不展示且不崩溃。

## 五、风险与兼容性

- **默认行为不回退**：玻璃球替换旧卡片属"同载体升级"，绑定态驱动逻辑不变；保活全部为新增层，不修改既有 tick/心跳/指令逻辑。
- **耗电**：daemon 5s 轮询仅为两次文件读取，可忽略；闹钟 60s 窗口批处理，系统会合并唤醒。
- **ROM 差异**：华为等激进省电 ROM 仍可能延迟投递；四层保活确保"最终一定恢复"，最坏恢复时间写入文档，不谎称秒级。
- **投影令牌边界**：MediaProjection 进程死即失效不可恢复（平台红线）；本方案以"无障碍通道为主 + 看屏会话主动恢复 + 按需引导"应对，录屏类确需投影时仍走一次用户确认。
