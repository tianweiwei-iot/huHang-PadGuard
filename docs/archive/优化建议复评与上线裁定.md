## 二、复评新发现（原审计遗漏）

### N1：护航密码未设置时，**整个无障碍闸门失效——包括宣称"不可关闭"的设置圈禁**

`OperationGuardAccessibilityService.kt:95-96`：

```kotlin
// 密码未启用 → 闸门关闭，不做任何事
if (!manager.isEnabledNow()) return
```

这行在 `decide()` **之前**，意味着：家长只要没设置护航密码，三类拦截（设置页/安装器/受管应用）**全部不生效**——包括代码注释和上轮审计都宣称"不可关闭、关掉等于管控自毁"的设置页拦截。

**这违反了原则 1 的"隐性约定"判定**：注释语义（设置拦截不可关闭）与实际行为（受密码开关控制）不一致，防线状态取决于一个没人保证的前置条件（家长是否设了密码）。无 DO 主线下这是**比 C1 更危险的洞**——C1 是"无障碍被关后失活"，N1 是"无障碍开着也没用"。

**修正方案（两道保险）**：
1. `decide()` 拆层：`REASON_SETTINGS` 分支提到 `isEnabledNow()` 判断**之前**——密码未设置时对设置页只顶回（GLOBAL_ACTION_BACK）不弹密码框，同时上报"密码未设置"告警。让行为与注释语义一致
2. 绑定流程强制项：家长端绑定成功后引导页强制设置护航密码（服务端 GuardPasswords 下发链路现成），未设置前家长端首页显示黄色提醒

### N2：C1 的实现有模块分层陷阱，原方案"加一条检测项"会破坏分层

`TamperDetector` 在 `core:engine` 模块，而 `GuardA11y`（无障碍启停探测）在 `app` 模块。若按原建议直接注入，会造成 **core:engine → app 的反向依赖**，破坏孩子端唯一"规划态=实际态"的模块化（原则③第 4 问：Android 侧自身不一致）。

**修正方案（依赖倒置，主流手法）**：在 `core:engine` 定义接口 `GuardInfraProbe { fun accessibilityEnabled(): Boolean; fun usageAccessGranted(): Boolean }`，app 层实现并用 Hilt `@Binds` 注入；TamperDetector 依赖接口。顺带把 C8（使用情况权限失活）也用同一接口解决，一次改造消两个缺口。

## 三、需返工条目（原方案 → 修正方案）

### G1：从"照抄模式补参数"改为"统一归属校验组件重构"

**原方案问题**：审计已确认全服务端 **10+ 个 Service 各自复制了一份私有 `requireOwned`**（AppManage/Monitor/Statistics/ContentFilter/DeviceMgmt/Group/Device/PolicyExtension/Alert/Message/Unlock）。原建议给 Geofence"照抄再复制一份"= 第 11 份重复——正是原则 1 点名的重复代码 + 隐性约定（每份实现细节靠人肉保持一致，漏一处就是下一个 IDOR，G1 本身就是漏网证据）。

**修正方案**：
1. 新建 `security/DeviceOwnershipGuard.kt`：单一方法 `requireOwned(userId, deviceId): Device`（校验设备存在 + 归属，抛现有错误码）
2. **删除全部私有副本，让编译器驱动替换**——私有方法删除后所有调用点必须改，机械且不漏（比逐个"改完自测"可靠）
3. GeofenceService 的 4 个方法 + 2 个 Controller 入口随之补上 userId 参数

**四问自检**：① 消除重复与漏网根因 ✓ ② 依赖注入 + 单一职责，Spring 标准手法 ✓ ③ 新增越权面只改一处 ✓ ④ 后端内部收敛，Android 侧无感 ✓

### G7：从"内存 Map 限流"改为 Resilience4j RateLimiter

**原方案问题**："内存 Map 即可"是自造限流——计数窗口边界、并发竞争、内存清理全是手写坑，违反原则 ②。

**修正方案**：引入 `Resilience4j`（Spring Boot 生态限流事实标准，生产成熟）。登录/发码/绑定码消费三个入口各挂一个 RateLimiter（按 IP+账号维度）。单实例内存态即可；未来多实例时 Resilience4j 亦有 Redis 集成路径，不留迁移债。

### G5：从"加排除名单"升级为"配置 fail-fast"

**原方案问题**：加排除名单只修了表症。真正的病根是**配置错误只能靠运行时撞上才知道**——`mock-pay-enabled=true` 时 `PaymentVerifier` 放行一切回调（`PaymentVerifier.kt:67-70`），这类配置隐患不止一处。

**修正方案**：
1. `/v1/billing/notify` 加入排除名单（注释意图与实现对齐）
2. 新增启动期配置断言（`ApplicationRunner`）：`mock-pay-enabled=true` 且非 dev profile → **拒绝启动**（与 guard.sh"防呆前置"思路一致）；同理断言生产 profile 下 JWT 密钥已显式注入

### C2：从"继续硬编码 ROM 清单"改为"内置默认 + 服务端配置下发"

**原方案问题**：继续往 `SECURITY_CENTER_PACKAGES` 里加包名 = 每适配一个 ROM 发一版 APK，ROM 适配永远滞后于市场保有量——这是结构性脆弱，不是清单长短问题。

**修正方案**：把"设置包/安全中心/卸载器"三张清单改为**策略包字段**（服务端可运营更新，孩子端 `UPDATE_CONFIG` 指令通道现成），客户端保留当前硬编码清单作为**内置兜底默认值**（离线/老服务端兼容）。这是特征库类产品的标准做法（竞品的"应用识别库"同模式）。

## 四、需验证后再定的条目

### C3（卸载自身特判）：先用 `event.className`，不开内容读取

`operation_guard_accessibility.xml:19` 明确 `canRetrieveWindowContent="false"`（隐私卖点，注释 :38-39 已声明"不读取任何界面内容"）。好消息：`TYPE_WINDOW_STATE_CHANGED` 事件的 `getClassName()` 由系统填入事件本身，**不依赖内容读取权限**。方案：拦截器判定升级为 `pkg + className` 二元组（如 `UninstallerActivity` vs `InstallInstalling`），**不开启 retrieveWindowContent**——保持隐私边界不变。上线前需真机验证各 ROM 事件 className 取值（华为/小米/OPPO 各一台，与 C2 的真机适配合并做）。**验证不通过则降级为"安装器页一律需密码"（现状语义），不阻塞上线。**

### C9（白名单无 DO 兜底）：产品决策，登记暂缓

`PolicyEngine.kt:288-290` 的放弃是显式设计决策（有注释论证），不属于"带病"。但低龄定位下白名单是高频用法，**上线前必须二选一**：① 产品层引导白名单用户开 DO；② 接受"白名单 = 仅桌面隐藏 + 15s 兜底"并在家长端明示。登记为 OPEN 项，不作为代码阻塞。
