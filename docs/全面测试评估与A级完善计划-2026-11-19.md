## 五、实施记录

### 第一批（本轮，服务端稳定性/测试有效性/门禁）

**N-01 分布式锁语义重构（稳定性 A- → A）——过程中发现更深根因**
- 初判：`RetentionCleanup.kt:65-66` / `UsageLogCleanup.kt:65` 的 `taskLock?.runExclusively(...) ?: body()` 在"抢锁失败返回 null"时 fallback 又执行 body，多副本互斥失效。
- 改为 `if (taskLock == null) body() else taskLock.runExclusively(...)` 后，**全量门禁暴露回归**：`UsageLogRetentionIntegrationTest` 2 例失败。深挖根因——**local/home 档 `flyway.enabled=false` + `ddl-auto=update`，而 `task_locks` 是无实体的裸表，这两个发布档位根本没有该表**；Spring 仍注入了真实 `TaskExecutionLock`，抢锁因"表不存在"降级为 false → 清理被跳过 → 用量表永久膨胀。旧写法的 fallback 歪打正着保住了单副本档。
- 正解：把"表不存在=单副本放行"从碰巧兜底**提升为锁内部显式语义**。`TaskExecutionLock.tryAcquire` 的异常分支用 `information_schema.tables`（表不存在返回 0 而非抛异常）区分：① 无锁表 → 放行执行；② 有表但写故障 → 跳过交健康副本。关键陷阱：若用 `SELECT count(*) FROM task_locks` 探测，无表会抛异常，与 DB 故障混淆导致单副本误判跳过——已规避并写进注释。
- 行为测试：`TaskExecutionLockTest` 将 `lock table failure degrades to skip` 拆为两条——`missing lock table runs body in single replica mode`（无表放行）+ `lock table write failure degrades to skip`（有表故障跳过）；`UsageLogCleanupTest` +2 例、`RetentionCleanupTest` +1 例（持锁跳过），全用真实 H2，不依赖 mock final 类。定向回归含此前失败的集成测试全绿。

**N-02 恒真断言行为化（测试有效性假绿消除）**
- 删除 `AlertTitleCoverageTest` 中对测试内局部常量的自证断言（`assertEquals("设备事件", fallbackTitle)` 一类）。
- `AlertServiceTest` 新增 `unmapped risk type falls back to readable Chinese title and message`：真实调用 `createFromEvent("dev1","SOME_FUTURE_TYPE",...)`，断言落库 Alert 的中文兜底标题/category，能真正拦住兜底退回英文枚举名的回归。

**N-03 BillingService 裸 NPE 消除（代码质量）**
- `ensureCanBind` / `ensureCanBindForChild` 的 `findByUserIdForUpdate(userId)!!` 改为 Elvis + `BizException(SUBSCRIPTION_REQUIRED)`（分端 audience），并发下订阅被删时返回业务错误而非 500。

**N-04 门禁用例数下限收紧（防假绿）**
- `launch-preflight.sh` 下限 1000/400/100 → 1100/600/140（实测 1227/779/165，留足余量）。

**验证**：
- 定向回归：TaskExecutionLockTest / UsageLogCleanupTest / RetentionCleanupTest / UsageLogRetentionIntegrationTest / AlertServiceTest / AlertTitleCoverageTest / BillingServiceTest 全绿（BUILD SUCCESSFUL）。

### 第四批（服务端订阅月末续费收缩修复，业务逻辑 A- → A）

**N-07 月末链式续费日期收缩（可单端 JVM 复现的真实缺陷）**
- 根因：`BillingService.plusMonths` 用 `LocalDate.plusMonths` 会把 1/31 夹到 2/28；`extend()` 又以 `maxOf(expiredAt, now)` 为基准连算，于是 2/28 再续得 3/28 —— 每次续费累积少 2~3 天，月底到期的月卡/年卡用户几年后到期日从 31 号漂到 28 号。现有测试只测"从今天起算 +12 月"，从不覆盖月末链式续费。
- 修复：`plusMonths` 加**月末锚定**——基准日若是所在月最后一天（`base.dayOfMonth == base.lengthOfMonth()`），目标日也取目标月最后一天（`date.withDayOfMonth(date.lengthOfMonth())`），使 1/31→2/28→3/31 稳定停在月末。不加列、不碰 Flyway、不动不变量。
- 行为测试（`BillingServiceTest` +2）：`renewals chaining from month end keep the month-end anchor`（1/31 连续两次 → 3/31）+ 反向对照 `non-month-end renewals advance by the same day of month`（1/15 → 2/15，证明普通日期不被误伤）。
- **红→绿验证**：修复前月末测试在断言行 FAILED、对照测试 PASS（证明 bug 真实、非测试写错）；修复后 BillingServiceTest 全绿。
- 全量门禁 GO：服务端 1233（+2）+ 孩子端 779 + 家长端 165 = **2177 用例，0 失败**，lint 0 Error。

### 第五批（服务端审批时长下界 + 健康探针存储覆盖）

**N-08 临时解锁下发非正时长（三端口径不一致，可单端 JVM 复现）**
- 根因：`UnlockService.approve` 的 `effectiveDuration` 整机分支只 `minOf(requested, 120)` 夹上界、带包名分支上下界都不夹；而记账侧 `grantWholeDeviceMinutes` 已 `coerceIn(1, max)`。家长填 `-5`（或孩子上报负值家长未重填）时，下发 `-5`、账面却 +1 分钟。孩子端 `CommandExecutor.kt:215-217` 对 `durationMinutes<=0` 直接 ACK `BAD_PAYLOAD` 拒绝整条指令 —— 结果是「家长点同意、账面加时、设备毫无反应」，正好违反该方法注释自身承诺要避免的事故。
- 修复：整机分支 `coerceIn(1, MAX_DAILY_EXTEND_MINUTES)`、带包名分支 `coerceAtLeast(1)`，下发/入账/工单三端口径统一。不动不变量。
- 行为测试（`UnlockServiceTest` +2）：整机与带包名两分支各一例，传 `-5`，断言下发 `DURATION_MINUTES==1`；整机分支额外断言 `claimApprove` 也用 1（与记账一致），带包名分支断言不改动每日额度。
- **红→绿验证**：修复前两例均 FAILED（实际下发 `-5`）；修复后 `UnlockServiceTest` 全绿。

**N-09 `/health` 只探 DB、不探文件存储（上线可观测性缺口）**
- 根因：`HealthController.health()` 仅 `probeDatabase()`。home 发布档文件落 `./uploads`；磁盘满 / 只读挂载 / 目录被误删或换成普通文件时，截图/录屏/素材上传静默失败，而 `/health` 仍报 `UP`，运维无从第一时间发现。
- 修复（单文件）：新增 `probeStorage()` —— `storage.dir` 不存在时按 `FileStorageService` 同款语义 mkdirs（目录缺失本身不算故障），实际写删一个临时探针文件验证可写；结果缓存 30s 避免守护脚本高频落盘；返回体新增 `storage:UP/DOWN`，DB 或存储任一 DOWN 即 503。守护脚本只 grep `ready=true`，新增字段不破坏既有消费方。

### 第六批（服务端 MQTT 实时告警路由修复）

**N-10 HIGH 风险实时告警被静默丢弃（严重，可单端 JVM 复现）**
