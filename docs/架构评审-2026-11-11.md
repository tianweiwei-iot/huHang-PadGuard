# PadGuard 平板管控系统 · 架构评审（2026-11-11）

> 评审视角：企业级 SaaS 架构师。评审依据：四端源码（护航成长 / 护航控制端 / padguard-server / padguard-admin）+ 部署编排（docker-compose.prod.yml）+ 运维文档（上线推进/决策清单、云端部署评估、发布运行手册）。
> 评审目标：**不做大规模重构，优先保证明天小规模上线（受控内测 10–20 家庭）稳定。** 故将结论严格分为【上线前必须调整】与【后续迭代重构】。

---

## 0. 一句话结论

这套系统的**可靠性内核（指令幂等、离线策略、消息双通道降级）工程成熟度很高，是真实亮点，明天不要动它**；当前最大的架构特征不是"有缺陷"，而是**为单实例而设计**——所有"赢家裁决"都已落库（DB 行锁串行化），但所有"在线/会话/流分发"状态都留在 JVM 内存里。这决定了：**明天单实例跑得稳，但加机器前必须先把这些内存态抽走。** 明天上线真正要补的是**运维兜底与清场**，不是架构重构。

### 1.2 三条核心链路

1. **指令下行**：家长 REST → `CommandService.issueCommand`（HMAC 签名 + `msg_id` unique + 落库 `PENDING`）→ `afterCommit` 内 `mqttGateway.publish` QoS1 → 孩子端 `CommandGate` 验签+三层幂等 → `CommandExecutor` 执行 → `ack` 上行 → `applyAckIfOpen` 条件 UPDATE 终态 → WS 推家长。
2. **数据上行**：孩子端 心跳/日志/事件/定位/截图 → IngestService 落库（`event_id`/`log_id`/`msg_id` 去重）→ 触发聚合与告警。
3. **实时推送**：设备上线/离线、新告警、指令结果、看屏就绪 → WS 推家长端（运行期账号复核：登出/冻结即时掐断）。

## 2. 七项重点检查结论（逐条）

| 检查项 | 结论 | 评级 |
|---|---|---|
| 模块耦合 | 四端职责清晰；但 4 处 JVM 内存态与服务端"单实例"假设隐式强耦合 | ⚠ 单实例 OK / 扩展即破 |
| 职责划分 | DPC=系统桥、Launcher=呈现、GuardService=调度、PolicyEngine=判定、server=持久化编排、mosquitto=传输、PG=存储，划分合理 | ✅ 清晰 |
| 状态同步 | Device↔Server 双通道共用 `pendingForPolling`+ACK 终态不可回退；Parent↔Server WS+10s 轮询兜底 | ✅ 健壮 |
| 心跳机制 | "存活即轮询"（3s 拉指令兼心跳，零额外流量）+ 内存 registry 1s 扫描，实测 ~5.4–6.6s 翻转；遗嘱去抖 3.5s | ✅ 巧妙 / 内存态绑定单实例 |
| 离线策略 | 本地 PolicyEngine 全判定 + 冷启动预热 + 受信钟防改时间伪造日切 + retained 策略通知 | ✅ **最强项** |
| 指令幂等 | 三层幂等（本地 DB claim / 内存 LRU / DB 条件 UPDATE）+ `msg_id` unique + HMAC + 补发白名单 fail-closed | ✅ **最强项** |
| 消息可靠性 | QoS1 + retained + LWT + 双通道（MQTT 不可达→HTTP 长轮询）降级 | ✅ 健壮 / broker 单实例 |

### 2.1 离线策略（最扎实，已达成"离线照样管得住"）
- 本地 `PolicyEngine.tick()` 基于**本地缓存策略**做时段/限额/护眼/宵禁判定，全程不依赖服务端。
- `AppGuardPolicyStore` 冷启动同步预热，消除历史 fail-open 空窗。
- **受信钟**：以 `serverTime ± RTT/2` 校准，`CommandGate` 用校准后时间判时效——孩子改系统时间伪造不了日切、抹不掉已用时长（已诚实写入家长端"管控能力说明"弹窗）。
- 日总时长改**服务端权威会话**驱动，规避三端时钟漂移。
- 已知边界（软管控固有限制，已披露）：改系统时间可拨动"墙钟时段"判定，DO 也根除不了。

### 2.2 指令幂等（端到端成熟）
- 设备端 `tryClaim(msgId)`（本地 DB 原子占位）→ `markExecutedIfFirst`（内存 LRU 512）→ 服务端 `applyAckIfOpen`（双键 `msgId+deviceId` + 白名单终态不可回退，DB 行锁裁决唯一赢家）。
- `msg_id` 唯一约束；HMAC-SHA256 验签；`expiresAt` 5min + 时效封顶 +15min。
- 补发白名单 fail-closed：`LOCK_SCREEN/UNLOCK/采集/消息` 不在补发名单，避免离线 8h 后补发"临时解锁"类指令。

### 2.3 消息可靠性（双通道韧性）
- MQTT 下行 QoS1 + retained 策略通知 + LWT 遗嘱（`online:false` retain）+ `isCleanSession=false`（离线堆积重放）。
- 孩子端连败 3 次 → 降级 `TransportMode.POLLING`；服务端 MQTT client 为 null → 全量降级 HTTP 长轮询（`notifyWaiters` 兜底）。
- 上行事件 `event_id` 唯一 + `insertIgnoreConflict`，避免 QoS1/HTTP 重试重报。

## 3. 瓶颈点

1. **看屏带宽是真实成本大头**（非架构瓶颈）：每路双向 8–16 Mbps（已降码率 4fps@640p + 满员 3 路限制 + 家长端背压）。靠"按流量计费 + 少量保底"即可，无需高配 CPU/内存（视频仅字节转发不转码，JVM 实测 350–430MB）。
2. **单机 DB 是容量上限**：规模 500+ 后需 PG 读写分离；当前单实例 PG 是硬上限（也是 SPOF，见 §4）。
3. **内存态阻止水平扩展**：`DevicePresenceRegistry` / `CommandService.waiters` / `WebSocketPushService.sessions` / `ScreenStreamHub` 全在 JVM 内存——这是明天之后扩容的最大拦路虎，但**明天单实例无感**。
4. **指令 3s 轮询是 HTTP QPS 主来源**：MQTT 已默认启用，启用后 QPS 降约 70%；若某设备 MQTT 退化为轮询，单设备约 0.33 req/s，千台规模仍可控。

## 4. 单点故障（SPOF）

| # | 单点 | 证据 | 影响 | 明天是否可接受 |
|---|---|---|---|---|
| 1 | 单 Mosquitto broker | `docker-compose.prod.yml:39` 单 `eclipse-mosquitto:2` | Broker 宕机→全量降级 HTTP 轮询（功能不失效，实时性降） | ✅ 有降级兜底 |
| 2 | 单 PostgreSQL | `:24` 单 `postgres:16` | DB 宕机→全系统不可用 | ✅ 卷持久化+备份可恢复 |
| 3 | 单 Nginx | `:51` 单节点 | 发布窗口 502（已有 healthcheck 缓解） | ✅ |
| 4 | 单 app 实例 | `:68` 无 replicas | 宕机→全站不可用；且内存态强制"只能单实例" | ✅ 受控内测规模可接受 |
| 5 | 4 处 JVM 内存态 | presence / waiters / WS sessions / stream hub | 多副本时互相看不到对方状态→误判离线/推不到/流断 | ⚠ 仅扩展期发作 |

**结论**：四大核心服务全部单实例、同机编排，本质是"单机即全站"。`restart:unless-stopped` + `healthcheck` + 卷持久化 + DB 备份提供了基础韧性，**对明天 10–20 家庭的受控内测完全够用**。真正的消除方式是后续 HA 改造，而非明天动。

## 5. 扩展性优化（按规模分档，均属后续）

- **短期（<500 设备）**：单实例足够；确保 MQTT 启用关高频轮询；带宽按流量计费；看屏降码率已做；对象存储加生命周期+CDN。
- **中期（500–3000）**：app×2 + SLB + **Redis**；PG 高可用版；EMQX×2；对象存储。Redis 是承上启下的关键——抽走 §4 的内存态。
- **长期（3000+）**：PG 读写分离 + HikariCP 调优；EMQX 集群；看屏独立高带宽节点。
- **最大降本杠杆（改动小、收益大）**：**看屏局域网直连**——心跳已带 `network.ip`，家长在家时直连平板、服务端带宽归零；跨公网回落中转。比 WebRTC（TURN 成本+打洞失败+故障面）更稳更省。

## 6. 解耦方案（后续迭代，非明天）

1. **内存态外移**：`DevicePresenceRegistry / waiters / WS sessions / ScreenStreamHub` → Redis（在线态、长轮询唤醒信号、WS 会话注册、流分发 Pub/Sub）。这是"可水平扩展"的硬前提。
2. **文件存储抽象**：`FileStorageService` 已实现"改一处即换 OSS/MinIO"的预留；生产把 `./uploads` 本地目录换成对象存储（多实例文件互通 + 防磁盘满）。
3. **跨实例事件 fan-out**：引入 Redis Pub/Sub 或消息总线，让 WS 推送与看屏分发在多实例间广播。
4. **MQTT 客户端库统一**：服务端 Paho **v5**、孩子端 Paho **v3**（Mosquitto 2 可互通，但维护/排障成本高）。建议抽象 `Transport` 层并统一到 v5。
5. **多租户 ACL 收窄**：`mosquitto/aclfile` 的 `broadcast` 仅按 `%u`(deviceId) 收窄、未按租户收窄——多租户形态下设备可订阅他租户广播，属已知取舍；单租户（家庭）形态无影响，后续按 `tenant` 维度收紧。
6. **生命周期清理**：当前无文件/日志自动清理任务（云端评估 §5 已列），对象存储上生命周期规则 + 定时清理任务。

## 7. 【上线前必须调整】vs【后续迭代重构】

### 7.1 【上线前必须调整】—— 不做会直接影响明天或带来合规/安全风险（均为小动作，非重构）

| 项 | 为什么明天必须 | 动作 |
|---|---|---|
| **A. TLS 证书** | 公网 8883/443 用自签证书，Android 无法验证 → 真实设备连不上。若为"受控内测（真实设备公网连接）"，这是**硬阻塞** | Let's Encrypt（免费，需域名+80 校验）或商业 DV/OV；部署到 nginx；certbot 自动续期 |
| **B. `uploads/` 清理** | 460 个测试样本，含 `shell.php.png` / `evil.png` 等探针文件，随版分发或经 nginx alias 暴露=安全事件 | 发布前跑 `clean-uploads.sh --prune`（按引用校验隔离），人工复核后清空 |
| **C. 源码密钥字面量复核** | 发布运行手册 §8 标注"服务端源码疑似含密钥字面量，待人工复核"——安全红线 | 上线前 `grep` 全仓确认无真实密钥/口令入库（`.env` 已 gitignore；`password=""` 等为空即可） |
| **D. DB 备份 + 上线前手动备份一次** | 单机架构下 PG 是核心 SPOF，无备份=宕机即数据全丢 | `backup-db.sh` 已存在；配置 cron 定时 + **上线前至少手演一次恢复**（确认可回灌） |
| **E. 看屏长连接（核对项，已满足）** | nginx `proxy_read_timeout/send_timeout 600s` 与后端异步超时一致，WebSocket 升级头已透传 → **已正确配置，无需改**；仅须确认后端 `async.request-timeout=600000` 未被改小 | 确认一次即可 ✅ |
| **F. 真机回归 R-01~R-11（风险明示）** | 文档列为"公开上线硬阻塞"，但环境无硬件、设备 AP 隔离跑不了；单测已全绿（服务端 1142/0、孩子端 223/0、家长端 115/0） | 受控内测可带"真机回归待补"风险上线，**发布说明须明示**；上线后 7 天内补真机（R-09 改时间绕过、R-10 非DO 自愈最该优先） |
| **G. 基础存活告警（强烈建议，低工作量）** | compose 有 healthcheck+restart，但**无主动故障告警**→半夜挂了第二天才知道 | 外部 uptime 探活，或 cron 探 `/health` 推微信/邮件；至少"单机宕机有人知道" |
| **H. 密钥 env 确认注入** | `PADGUARD_JWT_SECRET` 在 compose 用 `:?` 强制必填（避免随机写文件导致重启掉线/多实例互不认）；`.env` 已由 `gen-env-secrets.sh` 生成强随机 | 确认 `.env` 已落地且 gitignore 生效，JWT/BCrypt/MQTT 凭据均为强随机 ✅ |

> 说明：合规类（ICP 备案、隐私政策法务复核、发布签名 keystore 离线备份、微信商户资质）docs 标为 `owner=外部`。**首版可留空/暂缓**（微信支付默认 fail-closed 置灰、隐私政策先用已落地的弹窗告知），但 ICP 备案与 TLS 是公网运营前提，须明确排期，不可无限期拖延。

### 7.2 【后续迭代重构】—— 与明天稳定无关，规模/多租户到来时再做

- 内存态外移 Redis（presence / waiters / WS / stream hub）→ 多副本前提
- 文件存储本地 → 对象存储（OSS/COS）+ 生命周期
- broker / PG / nginx / app 单实例 → HA 集群（规模 500+）
- MQTT 客户端库统一（v3/v5）
- aclfile broadcast 按租户收窄（多租户形态）
- 看屏局域网直连降本（心跳已带 `network.ip`）
- 支付/短信真实渠道接入（首版留空 fail-closed）
- 文件/日志自动清理任务

## 8. 给架构师的最后建议

1. **明天别重构**：可靠性内核（幂等、离线、双通道）已成熟，动它风险远大于收益。把精力放在 A/B/C/D/G 的运维兜底与清场上。
2. **把"单实例"当作明确的设计契约写进运维手册**：所有内存态都假设单 app 实例；任何"加一台 app"的冲动都必须先完成 §6.1 的 Redis 化，否则会引入"误判离线/推不到/流断"的诡异故障。
3. **真机回归是明天之后第一优先级**：R-09（改时间绕过时段）、R-10（非DO 强停自愈）是软管控边界的最高考验，单测覆盖不了跨 ROM/跨进程行为。
4. **监控要从 Day 1 有**：单机全站架构下，没有告警 = 盲飞。G 项是性价比最高的"上线前"动作。
