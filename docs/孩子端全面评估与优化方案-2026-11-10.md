# 孩子端全面评估与优化方案（2026-11-10）

> 评估对象：`护航成长`（PadGuard 孩子端 Android 应用，包名 `com.padguard.child` / debug `.debug`）
> 评估方法：三个并行只读深度审计（架构与功能 / 安全与防绕过 / 测试覆盖与依赖质量）+ 关键源码复核
> 评估目标：全面评估架构、逻辑、功能、安全，并按「最新、最成熟、最稳定」的工程实践做优化完善
> 约束基线：最小改动、不虚构能力、三端 BUILD SUCCESSFUL + 孩子端 lint 0 Error 为门禁、暂不提交 git、DO/非 DO 能力分级必须诚实

---

## 0. 一句话结论

孩子端**架构分层合理、依赖方向正确、Hilt 无环、核心设计约束（三端一致计时 / 锁屏原因集合 / 单调时钟防改时间 / MQTT 离线堆积 / 进程重启自愈）均已扎实落地**，功能完整度高、无明显半成品或死代码。真正的短板集中在两处：**关键路径缺少行为测试**（命令分发、连接重连、策略聚合、日切恢复零行为测试，仅有的 3 个源码扫描契约测试脆弱），以及**少量可低成本关闭的安全/质量缺口**（备份提取未显式收敛、应用自身完整性/重打包无校验）。依赖整体健康，仅 Paho MQTT（停止维护）与 Compose BOM/Room（落后约一年）值得规划升级但**非紧急**。本轮据此做了「测试加固为主 + 安全 lint 收敛为辅」的优化，对高风险架构变动（迁移 MQTT 库、重构 GuardService、升级构建依赖）明确列为「建议项，本轮不执行」以守住门禁。

## 1. 架构评估

### 1.1 组件与职责（已落地，无缺失）
- **Application**：`PadGuardApplication` —— 进程级守护自愈 + 受信钟打底 + 安装分类探测。
- **Service**：`GuardService`（守护心脏，15s 主循环：采样/心跳/自检/会话同步/效果订阅/看屏恢复）、`GuardDaemonService`（`:daemon` 独立进程互保）、`GuardWatchdogService`（JobScheduler 看门狗）、`ScreenCaptureService`（MediaProjection 看屏/录屏）。
- **Activity**：`MainActivity`/`KidHomeActivity`（自定义 Launcher 兜底）/ 绑定流程 / `LockScreenActivity`（无解锁入口锁屏页）/ `AppAccessGateActivity` / `AppBlockActivity` / `GuardUnlockActivity` / 消息霸屏 / 玻璃球 / 无障碍引导。
- **Receiver**：`BootReceiver` / `DayRolloverReceiver`（日切加速）/ `GuardAlarmReceiver` / `LockBoundaryAlarmReceiver` / `PadGuardDeviceAdminReceiver`（DO 锚点）。
- **无障碍服务**：`OperationGuardAccessibilityService`（操作闸门软拦截核心）。
- **core 分层**：`common` → `data`（Room/Repository）→ `engine`（策略编排/Enforcer/锁控）→ `transport`（MQTT/HTTP）。`engine` 的 Enforcer 是无 Android UI 依赖的纯逻辑，可 JVM 单测；app 层是唯一组合根，承担所有平台副作用落地。

### 1.2 评估结论
- ✅ **依赖方向正确**：core 不反向依赖 app 实现细节（必需的反向依赖已下沉为 `GuardInfraProbe` 接口 + `@Binds` 注入）。
- ✅ **Hilt 注入图无环**：`@Singleton` 单例（PolicyEngine / LockController / 各 Enforcer）生命周期贯穿进程，与守护语义一致；GuardService 用**自有** CoroutineScope（非 `@ApplicationScope`），避免服务重启叠加第二套心跳——注释充分、设计正确。
- ✅ **并发模型以「单主循环协程 + 显式锁」为主**：`PolicyEngine.applyMutex` / `UsageSessionManager.refreshMutex` / `MqttTransport.connectMutex` / `LockController.stateLock` 串行化关键区；主循环各子任务 `runSafely` 包裹，单点异常不拖垮整轮。
- ⚠️ **架构脆弱点（中）**：`GuardService` 约 3194 行、60+ 注入字段，是实质性 God object。已有 `LockScreenPresenter`/`MessageOverlayController` 等先例可继续下沉协调器，但**重构风险高**，本轮不执行（见 §7 建议项）。

## 2. 核心逻辑评估（计时 / 锁屏 / 连接 / 日切 / 命令 / 自愈）

### 2.1 已扎实落地的逻辑
- **三端一致计时**：`UsageSessionManager` 用单调时钟 `liveRemainingMs()`（`elapsedRealtime` 而非墙钟）平滑倒计时，离线落盘恢复；`PolicyEngine.tick` 统一派生 `DAILY_LIMIT`，避免与 `syncAutoReasons` 冲突导致的锁屏闪烁。
- **锁屏原因集合**：`LockController` 用 `LockReason` 枚举而非布尔；`REMOTE` 落盘持久化，`AWAITING_START` 每轮重派生且 UNLOCK 压不灭（刻意设计），`syncAutoReasons` 差集同步自动原因。
- **日切重置**：`checkDayRollover()` 每 tick 本地独立执行（不等网络）+ `DayRolloverReceiver` 加速；跨日立即重置为「待确认」，不自动起表（A13 设计）。
- **连接可靠性**：MQTT `CleanSession=false` + 自动重连 + LWT 遗嘱 + QoS1 离线堆积；命令轮询在线 ≤3s、心跳 30s 兜底。
- **进程重启自愈**：四层（`:daemon` 进程互保 / JobScheduler 看门狗 / AlarmManager / BootReceiver）+ `Application.onCreate` 幂等补拉。

### 2.2 已识别并修复的脆弱点（前序轮次 + 本轮）
- 进程重建不启动守护（已在代码树落地：Application 补拉 + 锁屏页前台补拉 + `REASON_PROCESS_RESTART` 幂等分支）。
- 锁屏页跨日 UI 不更新（已改为 `lockController.state.collect` 实时跟随）。
- 联网恢复只 `uploadPending()` 不主动对账（已补 `refreshPolicy()` + `refresh()` + `drainPendingCommands()`）。
- 锁屏页亮屏即本地日切（`onResume` 调 `checkDayRollover()`）。
- **本轮新增行为测试**守护上述逻辑（见 §5.2）。

### 2.3 逻辑评估结论
核心逻辑**正确且健壮**，设计上已经闭合「掉线 → 锁屏跨日 → 联网对账 → 解锁/起表」链路。剩余风险主要在「非 DO 设备架构天花板」（见 §4）与「离线期间远程指令固有不可达」（网络事实），二者均非代码内可根除。

## 4. 安全评估

### 4.1 强项（已确认无误）
- **时间篡改双轨钳制**：`TimeProvider` 护栏不让篡改生效 + `TamperDetector` 检测让篡改可见，离线即生效。
- **高敏凭据**：`AuthRepository` 用 Keystore AES-GCM 加密 `deviceToken/mqttPassword/hmacSecret/childToken` 存 DataStore，家长密码永不落库；`CredentialCodec` 处理密钥丢失救砖逻辑。
- **指令三道关**：时效（受信钟 + 签名封顶）+ HMAC-SHA256 + `msgId` 幂等；上行也带 HMAC 信封。
- **MQTT 默认 TLS**：`ssl://` 启用 TLS，系统 CA 或自签 CA 钉死。
- **明文传输闸门**：`EndpointSafety` 对公网 `http://`/`tcp://` 一律 Rejected 永不落盘；`ALLOW_CLEARTEXT_PUBLIC` 默认 false（release 拒公网明文）。
- **DO/非 DO 能力如实分级**：非 DO 下「声明但做不到」的项如实回 `UNSUPPORTED` + 上报 `POLICY_DEGRADED`，不夸大。

### 4.2 安全脆弱点 Top（按可利用性）
| 排名 | 项 | 风险 | 类别 |
|---|---|---|---|
| 1 | 非 DO 设备锁屏可被手势滑走/分屏撕开 | 高 | **已知红线（架构天花板）** |
| 2 | 非 DO 设备可卸载/强停（无 `setUninstallBlocked`/`forceStopPackage`） | 高 | **已知红线（架构天花板）** |
| 3 | **缺少应用自身完整性/重打包/安装来源校验** | 中 | **本轮识别的可改进项** |
| 4 | `usesCleartextTraffic=true` 全局开关残存明文面（被 `EndpointSafety` 闸门拦截，OS 层未兜底） | 中 | 建议（本轮不改动，见 §7） |
| 5 | `hardLockAvailable()` 语义与实现不符（纯设备管理员+安全锁被判定硬锁分支却不真压 keyguard） | 中 | 代码清理/注释对齐 |
| 6 | root 检测仅文件/包名/`Build.TAGS` | 中 | 已知局限（端上无法阻止，仅检测上报） |
| 7 | `allowBackup=false` 已封备份，但 `dataExtractionRules` 未显式声明 | 低 | **本轮已修复（B1）** |

### 4.3 关于「应用自身完整性校验」（项 3）
当前 `PackageIdentity.isOwnPackage` 只做包名精确相等（防前缀伪造，做得好），**但没有任何对应用自身签名/安装来源的校验**。务实增量（纯检测 + 上报，不改管控行为，符合 `TamperDetector`「检测不是为了阻止，而是让失效可见」的设计立场）：

- **debug 构建运行于生产场景告警（A6，本轮已落地）**：`DEBUG_BUILD_ACTIVE` —— 用已有的 `admin.isDebuggableBuild` + 设备已绑定态（`authRepository.getDeviceId().isNotBlank()`），仅当"debug 构建且已绑定真实受管设备"时上报 NORMAL。release 构建 `isDebuggableBuild=false` 永不触发，**零误报**；开发/未绑定测试机（debug 但未绑定）属正常态不告警。已在三端同步：`core/data` 枚举、`core/engine` `TamperDetector.detectSelfIntegrity`、`app` 经 `PolicyEngine.scanTamper` 传绑定态、服务端 `AlertService.EVENT_TITLES` + `AlertTitleCoverageTest` 清单（该测试 3/3 已跑通）。
- **安装来源 / 重打包渠道校验（本轮仍不实现，理由变更）**：本应用经家长直装 APK 分发，**任何"非白名单渠道"上报都会在正常安装时误报刷屏**；且真正的重打包防护需服务端绑定握手校验签名（跨端协议），本地不虚构该能力。故不为它建白名单、不新增 `UNOFFICIAL_INSTALL_SOURCE`，避免"把正常分发当篡改"。若日后确定统一经官方商店分发，再回头补此半。

## 5. 测试覆盖与依赖质量评估

### 5.1 测试现状
- 约 **50 个测试类 / 490+ 测试方法**，以纯 JVM 单元测试 + Mockito 为主；纯函数（`UsageSessionRestore.plan`、`ScheduleEvaluator`、`LockController` 持久化语义、`TamperDetector`、`CommandSigningGolden`）覆盖良好。
- **关键路径行为测试缺失（高）**：
  - `CommandExecutor` 30+ 命令分发 / 去重 / 回执语义 —— **已有 4 例行为测试（A3 + A8），覆盖 UNLOCK 释放锁 / 重复 msgId 幂等 / START_TIMER_CONFIRM 弹确认 / 缺 requestId 坏载荷；其余 20+ 命令分支仍待补**
  - `MqttTransport` / `GuardService.observeDownlink` 重连重订阅 —— **零测试**
  - `PolicyEngine.tick` 策略聚合编排 —— **仅纯函数覆盖，无集成测试**
  - `UsageSessionManager.checkDayRollover` / `restorePersistedSession` —— **真实逻辑零测试**（仅纯决策层 `UsageSessionRestore.plan` 被测）
- **3 个源码扫描契约测试**（GuardRestartContract/AuthorizationCatalog/Hardening）：文本匹配脆弱，守护最关键自愈路径却无行为测试，重构改名即误报或漏报。

### 5.2 本轮测试加固（已新增，纯 JVM + Mockito）
新增两个行为测试类，**直接守护用户原始故障链路**：
- **`UsageSessionManagerTest`（12 例中的 8 例由本类承担）**：
  - 跨日重置：`checkDayRollover` 跨日→待确认、同日幂等、跨日且总开关关闭不弹确认、跨日后 `isAwaitingStart=true`；
  - `isExpired` 语义：active 耗尽→true、总开关关闭→false；
  - `confirmStart` 在线成功起表、离线按本地受信钟起表并标 `pendingStartSync`（守护「次日计时无法启动」）。
- **`CommandExecutorTest`（4 例）**：`UNLOCK` 释放全部锁定、重复 `msgId` 幂等（只执行一次）、`START_TIMER_CONFIRM` 弹确认框、缺 `requestId` 判坏载荷（守护「无法解锁 / 次日计时入口」）。
- 复用 `LockControllerTest` 的 write-through 内存 `SharedPreferences` mock 模式，规避纯 JVM 下 `android.util.Log` 未 mock 的坑（测试统一关闭 `Logger.enabled`）。
- **修复一处潜在竞态（A8 内）**：`START_TIMER_CONFIRM 弹确认框` 原写法 `async { exec.effects.first { … } }` 在 `replay=0` 的 `SharedFlow` 上跑出竞态——`execute()`（runBlocking 主线程）可能在后台收集协程完成订阅**之前**就 `tryEmit`，收集者永远收不到这条已被缓冲的值而 `first{}` 永久挂起。该测试此前从未被真正执行（见 §8.1 沙箱死锁），故这一 latent 缺陷一直藏在里面；改为 `async(start = CoroutineStart.UNDISPATCHED)` 让收集者在 `execute()` 前就在当前线程完成订阅注册，竞态消除、确定性通过。这同样是真实 Gradle 跑会偶发挂死的 flaky 点，修复属必要加固而非为跑通而改。

## 7. 明确不做 / 建议项（及理由）

为保证门禁稳过、不破坏既有契约，以下项**本轮不执行**，作为后续规划：

1. **迁移 Paho MQTT 库**（停止维护）：连接可靠性是用户原始故障核心，迁移属高风险架构变更，需独立评估维护型 fork（如 Eclipse Tahu）或自研轻量客户端，配真机长稳压测。
2. **升级 Compose BOM / Room / AGP**（落后约一年）：平滑增量升级，但需验 schema 迁移与 UI 回归，建议单独一轮、单独 git 提交、单独门禁。
3. **重构 `GuardService` God object**：拆分效果订阅/看屏恢复/通知/水印为独立 `@Singleton` 协调器，降低回归面——但重构风险高，须先有充分行为测试护体（§5.2 已起步）。
4. **应用自身完整性/重打包校验扩展**（§4.3 项 3）：**已落地一半（A6）**——「debug 构建误部署到已绑定设备」检测（`DEBUG_BUILD_ACTIVE`）已实装并通过三端契约测试。另一半「安装来源/重打包渠道校验」因本应用经家长直装 APK 分发、对非白名单渠道上报必误报刷屏，且真重打包防护属服务端绑定握手（跨端协议），**仍留作建议、本地不虚构该能力**。
5. **收敛 `usesCleartextTraffic`**：家庭局域网部署必须明文（release 直连本地服务端），全局开关被 `EndpointSafety` 闸门兜底，改全局会破坏核心部署场景——**不改动**，公网部署已走 Nginx TLS。
6. **`hardLockAvailable()` 语义对齐**（§4.2 项 5）：纯设备管理员+安全锁被判定硬锁分支却不真压 keyguard，属注释/语义清理项，低优先级。

- 现象：`gradle :core:engine:testDebugUnitTest` 在 fork 出测试 worker 后**零输出、不回传任何结果**。本次复现确认它**不是慢，是真死锁**：测试 worker 进程（PID 22328）线程数稳定在 228、CPU 长时间零增长（108s→108s 不动），与 `compile*` / `help` 等不 fork 的任务正常形成对照，可复现。

**测试执行门禁 —— standalone 纯 JVM 路线现已跑通（A8 后）**：
