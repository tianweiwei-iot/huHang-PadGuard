| 项 | 值 |
|---|---|

| IP | 公网 8.148.68.183 / 私网 172.18.6.128 |
| 已有服务 | 个人新机，无其他服务（与公司对公 8.217.22.251 4C8G 隔离，避免误伤公司其他后端） |
| 目录约定 | `/opt/padguard/`，与 RockiotTagBackend 的 `/opt/RockiotTagBackend` 目录同级（用户原话"放在 opt 下，跟 RockiotTagBackend 同级"指目录层级，非同机） |
| PadGuard 形态 | Spring Boot 单 jar（Java 17）+ PostgreSQL（Flyway V1~V25）+ MQTT broker + admin 静态目录（服务端同源托管 `:8090/admin/`） |
| 现有编排 | `docker-compose.yml` 已定义 postgres:16 + emqx:5.8 + app 三件套 |

### 2.2 关键拓扑事实（决定安全设计）

- **孩子端 MQTT 直连 broker**（paho v5，MqttTransport）→ 1883 必须**公网可达**
- 家长端走服务端 `/ws?token=<JWT>`，**不直连 broker**
- ⚠️ **最大风险**：当前 broker 无设备级认证（S1 批次 D 就是为这个设计的）。**无认证 broker 直接暴露公网 = 任何人可订阅/下发任意设备指令**。迁移必须带临时认证方案（见 M4）

### 2.3 部署形态（待确认，二选一）

| | 方案 A（推荐）：Docker Compose 全套 | 方案 B：jar + systemd + 中间件容器 |
|---|---|---|
| 内容 | postgres + broker + app 全在 compose | app 按宿主机 jar + systemd（与 RockiotTagBackend 同手法）；pg/broker 用容器 |
| 升级 | `git pull && docker compose up -d --build` | scp jar → systemctl restart |
| 隔离 | 最好，不污染宿主环境 | 中 |
| 与现有服务一致性 | 低（引入新运维方式） | 高 |

推荐 **A**：compose 已存在且验证过（test 环境同款），升级路径最短，与宿主机上 MySQL/traccar 等互不干扰。

**broker 选型（另一待确认）**：

| | EMQX 5.8（现 compose 所用） | Mosquitto |
|---|---|---|
| 内存 | 大（约 0.5~1GB） | 极轻（约 10~20MB） |
| 认证 | 内置 database/HTTP 认证，dashboard 好管 | password_file + ACL（**与批次 D S1 设计直接对齐**，Linux 下 SIGHUP 可热重载） |
| 判定 | 功能全但重 | **8G 共享机 + S1 设计契合 → 推荐** |

### 2.4 执行序列（我出命令、你在 ECS 执行并回贴输出）

**M1 目录与代码**
