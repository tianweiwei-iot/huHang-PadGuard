# PadGuard 云端部署资源评估

> 评估依据：本项目代码实测参数（`ScreenCaptureService` 常量、`application.yml`、孩子端上报间隔、服务端状态存储方式），
> 非通用模板推算。凡属推算项均已标注来源与假设。
> 成本为**参考区间**，实际以云厂商官网实时报价为准。

---

## 一、先看清这套系统的真实消耗模型

### 1.1 每设备的常态请求量（来自代码常量）

| 行为 | 代码常量 | 频率 | 折算 QPS/设备 |
|---|---|---|---|
| 指令轮询 | `COMMAND_PULL_INTERVAL_MS = 3_000` | 3s（活跃）/10s（空闲） | 0.33（活跃） |
| 用量同步 | `USAGE_SYNC_INTERVAL_MS = 10_000` | 10s | 0.10 |
| 心跳 | — | 约 30s | ~0.03 |
| 日志上传 | `LOG_UPLOAD_MIN_INTERVAL_MS = 60_000` | 60s | ~0.017 |
| 应用清单同步 | `APP_SYNC_INTERVAL_MS = 30*60_000` | 30min | ~0.001 |

**常态合计 ≈ 0.5 req/s/设备**（MQTT 启用后指令轮询可停用，可降至 ≈ 0.15 req/s）。

### 1.2 规模 → QPS 换算

| 在管设备数 | 常态 QPS（HTTP 轮询模式） | 启用 MQTT 后 |
|---|---|---|
| 500 | ~250 | ~75 |
| 1,000 | ~500 | ~150 |
| 5,000 | ~2,500 | ~750 |
| 10,000 | ~5,000 | ~1,500 |

### 1.3 带宽：真正的成本大头是「实时看屏」（已修正为双向）

代码常量：`LIVE_FRAME_INTERVAL_MS = 200`（目标 5fps）、`LIVE_FRAME_MAX_WIDTH = 720`。
源码注释原话：**「5fps 就是 1~2MB/s，家长端必然卡顿且画面永远是几秒前的」**。

**视频流路径（实测确认，100% 经服务端中转，且是双向的）：**

```
孩子端 --POST /api/v1/device/stream/up (4字节长度+JPEG, 长连接)--> 服务端 ScreenStreamHub
家长端 <--GET /v1/stream/{deviceId}/live (StreamingResponseBody)---- 服务端 ScreenStreamHub
```

- 服务端**只做字节转发，不转码**（`hub.publish` → `sub.poll` → 原样写出），CPU 开销极低。
- 因此每路看屏占用 **上行 1~2 MB/s + 下行 1~2 MB/s = 2~4 MB/s（16~32 Mbps）**。
  （初版文档只算了单向，此处已修正 —— 中转架构下带宽是双份的。）
- 常态非看屏流量：0.5KB/s/设备 → 1,000 设备仅 ≈ 4 Mbps（可忽略）。

| 设备规模 | 假设同时看屏比例 | 并发路数 | 中转带宽（双向） |
|---|---|---|---|
| 1,000 | 5% | 50 路 | ≈ 150~200 MB/s（1.2~1.6 Gbps） |
| 5,000 | 3% | 150 路 | ≈ 450~600 MB/s（3.6~4.8 Gbps） |

> ⚠️ 结论：**带宽规划必须由"并发看屏路数 × 2（双向）"决定，而不是设备数**。
> 也正因为服务端不转码，**CPU/内存可以按"普通 Web 服务"配置，不需要为视频预留**。

### 1.3.1 【已评估并否决】WebRTC P2P 直连

曾完整实现并验证过 WebRTC P2P（画面孩子端 ↔ 家长端直连、服务端只中转 SDP/ICE 信令），
服务端带宽可从 1.2~1.6 Gbps 降到约 4 Mbps。**但最终决定不采用**，原因：

| 顾虑 | 说明 |
|---|---|
| TURN 要额外付费 | 打洞失败时必须经 TURN 中继，自建或向云厂商采购都是持续成本 |
| 连不上影响体验 | 家庭宽带多在 CGNAT 之后、家长手机 4G 多为对称 NAT，约 15%~30% 的会话打洞失败 |
| 故障面变大 | 多了一整套信令会话、NAT 穿透、指纹校验、降级回退，线上排查成本高 |
| 收益可用降码率部分拿到 | 见 1.3.2，零成本即可省掉约一半带宽 |

**结论：保持"服务端中转"架构**。稳定性与可预测性优先于带宽最优解 ——
看屏是付费用户的高敏感功能，"连不上"比"多花点带宽"更伤。

### 1.3.2 中转架构下的零成本带宽优化（已实施）

既然走服务端中转，唯一的降本手段就是把每一帧压小。**不花钱、不改架构**：

| 参数 | 原值 | 现值 | 依据 |
|---|---|---|---|
| 推流帧率 | 5fps（200ms） | **4fps（250ms）** | 滑动时仍连贯；再降到 2fps 就明显是幻灯片 |
| 推流宽度 | 720 | **640** | 1920 宽屏缩到 640 约 33%，文字仍可辨认，体积降约 21% |
| JPEG 质量 | 60 | **50** | 60 以上对看清文字无明显增益，却多付 20%~30% 体积 |
| 并发观看上限 | 无限制 | **每设备 3 路** | 异常并发（重连未清理/脚本刷接口）会成倍放大带宽 |

两项配套保护：

- **家长端 `conflate()` 背压**：孩子端推 4fps、家长端解码跟不上时只保留最新一帧。
  丢帧可接受，延迟累积不可接受（否则会看到"几十秒前的画面"且内存持续上涨）。
- **满员返回明确错误码（2004）**而不是静默断开：静默断开会被家长端当成"孩子端停推"而无限重连。

重算后的带宽（1,000 设备、5% 并发 = 50 路）：

| | 原 | 现 | 变化 |
|---|---|---|---|
| 单路上行 | 1~2 MB/s | 0.5~1 MB/s | **约 -50%** |
| 单路双向 | 16~32 Mbps | 8~16 Mbps | 约 -50% |
| 50 路合计 | 1.2~1.6 Gbps | **0.6~0.8 Gbps** | 约 -50% |

> 省下的一半来自"少传一半的字节"，不依赖任何外部服务。
> 若要再进一步，下一步应做**局域网内网直连**（心跳已带内网 IP，同 WiFi 时家长端
> 直连平板、不经服务端）——它同样不需要 TURN、不花钱、也不受 NAT 影响，
> 失败时回退服务端中转即可。

### 1.4 存储

| 类型 | 实测/配置 | 说明 |
|---|---|---|
| 截图 | 55 KB/张（`_sample_shot.jpg` 实测） | JPEG |
| 录屏 | 目标码率 `RECORD_BIT_RATE = 4_000_000`（4Mbps），`MAX_RECORD_MS = 10 分钟` | 单次上限约 300MB；实测样本 175KB~1.96MB，实际取决于时长 |
| 单请求上限 | `max-file-size: 200MB` | 需按业务收敛，200MB 过大会被滥用 |

**必须配套生命周期策略**（当前代码无保留/清理逻辑）：
建议 OSS 规则：30 天后转低频存储，90~180 天后删除。否则存储只增不减。

## 二、架构约束（决定能不能水平扩展）

这几条是评估的**硬前提**，不解决则加机器无效：

### 2.1 长轮询 waiter 是 JVM 内存态 → 多实例必须启用 MQTT
`CommandService` 用 `ConcurrentHashMap` 保存挂起的长轮询回调，且**项目未引入 Redis/MQ**。
- 多实例部署时：家长在实例 A 下发指令，只能唤醒 A 内存里的 waiter；挂在实例 B 的孩子端收不到实时推送，
  退化为"等下一次轮询才拿到"（功能不失效，但实时性从 RTT 级降到轮询周期级）。
- **解法**：生产启用 MQTT（`application.yml` 默认 `mqtt.enabled: true`、`broker-url: tcp://emqx:1883`），
  指令走 EMQX 推送，不再依赖内存 waiter。此时长轮询自动降级为备用通道。
- ✅ 这符合"主流稳妥"：MQTT + EMQX 是 IoT/设备管控领域的标准做法。

### 2.2 文件存储当前是本地目录 → 云上必须改对象存储
`FileStorageService` 写 `./uploads` 本地目录。多实例时各实例文件不互通，且单机磁盘会满。
**解法**：改接 OSS / COS（代码注释已预留：`生产可换 MinIO/OSS，仅改 FileStorageService`）。

### 2.3 数据库：H2 → PostgreSQL
生产 profile 已是 `PostgreSQLDialect` + Flyway，本地 H2 仅用于开发/家庭部署。云上直接用 RDS PostgreSQL。

### 2.4 其他生产化项
- JWT：`padguard.jwt.secret` 留空会随机生成并写文件 → 多实例必须**显式注入同一把强密钥**（≥32 字节）。
- 定时清理：命令过期回收（`ExpiredCommandSweeper`）已有，但**文件/日志无清理任务**，需补。
- 看屏是长连接：`--spring.mvc.async.request-timeout=600000` 已在启动脚本中，云上负载均衡/网关的**空闲超时也要 ≥ 600s**，否则看屏被掐断。

## 三、推荐配置（按规模分档）

> 以阿里云/腾讯云为例。托管服务优先于自建（减少运维脆弱性）。

### 带宽计费策略（比"买多大带宽"更重要）

看屏是**低频突发**（家长偶尔看几分钟），不是 7×24 持续占用。因此：

- ❌ **不要按峰值买固定大带宽**：50 路峰值就要 1.6 Gbps，费用极高，但 99% 时间闲置。
- ✅ **按流量计费**（约 ¥0.5~0.8/GB）+ 少量保底带宽（5~10 Mbps 供常态上报）。

降码率后实测估算：1,000 设备、每天 10% 家长看屏、每次 3 分钟
→ 约 800 GB/月 → **约 ¥400~650/月流量费**，远低于买固定大带宽。

### 档位 A：试点 / 小规模（≤ 500 设备）

|---|---|---|
| 应用服务器 | ECS **2核4G** | 视频仅字节转发不转码，CPU 无压力；实测 JVM 350~430MB |
| 数据库 | RDS PostgreSQL 基础版 2核4G / 100GB | |
| MQTT | EMQX 单节点 2核4G | |

## 三·补 能否让家长端直连孩子端（P2P）？—— 可以，但要分场景

**结论先行：同局域网可直连且收益极大；跨公网建议先保留中转 + 降码率，WebRTC 作为中期优化。**

### 场景 A：家长与孩子在同一 WiFi（家长在家看孩子平板）→ **强烈建议直连**

- 孩子端起本地 HTTP/WebSocket 服务，家长端直连 `192.168.x.x:port`。
- **服务端带宽归零**，延迟从"经公网绕一圈"降到局域网内毫秒级，画质还能更高。
- 实现简单，不需要 WebRTC / STUN / TURN 那一套。
- 关键前提：家长端需要知道孩子端当前局域网 IP —— **心跳里已有 `Heartbeat.network.ip`**，
  服务端在设备详情/心跳响应里下发即可，改动很小。

### 场景 B：跨公网（家长在外面远程看）→ 直连受限于 NAT

- 家庭宽带普遍在运营商 CGNAT 之后、**没有公网 IP**，入站连接建不起来。
- 可行方案是 WebRTC（STUN 打洞 + ICE），但：
  - **对称 NAT 无法打洞**（命中率不低），仍要 TURN 中继 → 还是要服务器带宽；
  - 需引入信令服务、ICE、STUN/TURN 一整套，复杂度显著上升。
- IPv6 若能双方可用则可直连，但国内覆盖不稳定，不能作为主路径。

### 推荐落地路径（按性价比排序）

1. **【先做】局域网直连优先，公网中转兜底**
   家长端点「看屏」时，先根据服务端下发的局域网 IP 探测直连（TCP 连 `ip:port`，超时 300~500ms）；
   成功走直连，失败自动回落到现有 `/v1/stream/{deviceId}/live` 中转。
   家长无感知，且覆盖了"家长在家"这一高频场景，**服务端带宽可降一大半**。
2. **【同时做】大幅降码率**
   5fps@720p → 2~3fps@480p + 调低 JPEG 质量，带宽降 60%~75%，家长体感差别很小
   （看屏目的是确认"孩子在干什么"，不是看高清视频）。
3. **【中期可选】WebRTC**
   打洞成功时零服务端带宽。但建议等业务量起来、确认带宽成本真的成为瓶颈后再引入，
   不要为了"技术先进"提前背上信令 + TURN 的运维负担。

> 备注：无论哪种方案，`ScreenStreamHub` 的内存态分发同样有"多实例不互通"问题
> （与长轮询 waiter 同类）—— 多实例部署时家长和孩子必须落在同一实例，
> 或把 Hub 换成 Redis Pub/Sub / 消息队列。**这一点与是否直连无关，是独立必须解决的问题。**

## 四、成本优化建议（按收益排序）

1. **【收益最大】局域网直连优先 + 公网中转兜底**
   覆盖"家长在家看孩子平板"这一高频场景，**服务端带宽直接归零**（详见三·补）。
   心跳里已有 `network.ip`，改动量小：下发 IP → 家长端探测直连 → 失败回落中转。

2. **降低看屏码率/帧率**
   当前 5fps@720p ≈ 1~2MB/s（单向）。改 2~3fps + 480p + 调低 JPEG 质量，带宽降 60%~75%，
   家长体感差别不大（看屏是确认"孩子在干什么"，不是看高清视频）。

3. **看屏按需触发 + 闲置自动断**
   默认不看屏，家长点击才建流，超时自动 `live/stop`（已有）。避免长期空占连接与带宽。

4. **带宽按流量计费，不按峰值买固定带宽**
   看屏是低频突发，按量计费通常只有固定大带宽费用的十分之一。

3. **对象存储生命周期 + CDN**
   截图/录屏下载走 CDN 回源 OSS，减少应用服务器出口带宽（出口带宽比 OSS 存储贵得多）。

4. **启用 MQTT 停用高频轮询**
   指令轮询 3s 是 QPS 主要来源；启用 MQTT 后 QPS 可降约 70%，直接减少应用服务器数量。

5. **收敛单文件上限**
   `max-file-size: 200MB` 对截图/录屏过大，建议按业务收敛（录屏 ≤ 50MB、截图 ≤ 5MB），防止滥用打满存储与带宽。

## 六、结论（已按"中转架构"修正）

- **服务器 CPU/内存不需要高配**：视频只是字节转发、不转码，实测 JVM 仅 350~430MB。
  真正决定规格的是 HTTP QPS 与数据库，不是视频。
  → **起步 2核4G 即可**（初版给的 8G/16G 偏高，是按"视频转码"误估的）。
- **但带宽是双向的**：每路看屏 = 上行 1~2MB/s + 下行 1~2MB/s。初版只算单向，已修正。
- **带宽计费方式比带宽大小更重要**：看屏是低频突发，**按流量计费 + 少量保底带宽**，
  远优于按峰值买固定大带宽。1,000 设备典型用量约 ¥400~650/月。
- **最大的降本手段是"局域网直连兜底"**：家长与孩子同 WiFi 时直连，服务端带宽归零；
  跨公网再回落中转。心跳已带 `network.ip`，改造量小、收益大。
- **水平扩展的硬前提仍是三项**：启用 MQTT（指令推送）+ 文件改对象存储 + JWT 密钥注入。
  另外 `ScreenStreamHub` 也是内存态，多实例时需改为 Redis Pub/Sub 或让同一设备的推拉流落同一实例。
- **建议路径**：档位 A 起步 → 先做「降码率 + 局域网直连」两项 → 用真实并发校准模型 → 再按需扩容。
