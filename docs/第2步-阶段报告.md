### 关键语义（不是想当然，是代码约束倒推出的）

1. **回滚 = 取历史快照内容 + 分配更高新版本号**，绝不重发旧版本号。孩子端 `mergeWith` 只接受 `incoming.version > version`，低版本包会被静默丢弃。
2. **版本号一律走 `PolicyVersions.allocate`**（持 `devices` 行锁），不本地 `+1`；批量并发不会插出同号行。
3. **回滚幂等**：同一目标 + 同一窗口重复点击返回当前版本、`idempotent=true`，不新增行。
4. **回滚行跳过子表自愈**；家长任何一次主动改设置 → `rebuildPolicy` 写 NORMAL 行 → 回滚态自然结束。
5. **批量逐设备独立**：`deviceIds` 先去重、上限 200；每台单独 `requireOwned`；单台失败不影响其余，失败项统一文案不泄漏他人设备存在性。
6. **批量指令白名单**：只放行 `REFRESH_POLICY/FLUSH_LOGS/SHOW_MESSAGE/LOCK_SCREEN/UNLOCK/LOCATE/SCREENSHOT/SCREEN_RECORD/STOP_SCREEN_RECORD`；刻意排除 `SET_MANAGEMENT_ACTIVE`、`REVEAL_MANAGEMENT_UI`、`SET_RUNTIME_PERMISSION`、`SET_FEATURE_POLICY`。未来新增指令类型**不会自动进入批量通道**。
7. **MQTT 通知放 `afterCommit`**，Broker 抖动不让回滚整体失败；窗口 `to <= from` 直接拒；历史包 JSON 损坏拒回滚（绝不写空包，那会把设备放开成不管控）。

## 4. 架构缺陷：两套方案（针对 S2-01 的深层张力）

根因：**服务端把「子表」当唯一事实源，`packageJson` 是派生物**；而"版本回滚"天然要恢复一个历史快照，两者定义上冲突。

### 方案 A · 低成本快速版（本批采用）

给策略行加 `source` 标记，ROLLBACK 行跳过 `ensureRebuilt`；家长主动改设置自动退出回滚态。
- **代价**：小（1 张迁移 + 3 处逻辑 + 独立 Service），无需动孩子端协议，立即可上线试点。
- **残余**：回滚期间家长端设置页显示的是子表旧值，需 UI 用 `rollbackActive` 明确标注；批量非原子。
- **适用**：≤500 台试点、以"能真正退回上一个已知可用策略"为目标的运维刚需。

### 方案 B · 长期重构版

每次策略写入时**同时存一份子表快照**（`policies.substate_json` 或独立 `policy_snapshots` 表）；回滚 = 反序列化目标版本的子表快照 → 回写子表 → 走 `rebuildPolicy` 产出新版本。
- **收益**：子表与下发包始终一致，家长端设置页与设备执行状态**天然一致**；可做灰度发布、按分组百分比放量、冲突裁决；批量可基于 Outbox 事件流做至少一次投递与死信队列。
- **代价**：大。需为所有历史行补快照（存量无数据）、改所有子表写入点、引入事件流与分布式锁；且要等 `⟦TBD-1/2/4⟧` 业务口径定型后才能定字段。
- **建议**：A 已闭环上线阻断项；B 在第三步安全整改与家校模型拍板后单独立项。
