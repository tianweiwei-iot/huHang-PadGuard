# PadGuard 防破解 / 防绕过安全评估与加固方案

> 范围：孩子端 `护航成长`（含自定义 Launcher / DPC）、家长端 `护航控制端`、服务端 `padguard-server`  
> 目标：评估用户绕过管控的 7 类手段，定位权限/接口/传输缺口，给出**明天上线前可落地的低成本加固**。  
> 评估依据：直接审计源码（见各条 file:line），非凭空推演。

---

## 〇、总论：一切绕过的天花板是「设备所有者（DO）」

本系统的防御强度由**控制权态**一锤定音（见 `DeviceAdminBridge` 的 `controlMode`：LEGACY / DEVICE_ADMIN / PO / DO）。

| 能力            | 非 DO（软管控，默认） | 设备所有者 DO（硬管控） |
| ------------- | ------------ | ------------- |
| 卸载 / 强停 / 清数据 | ❌ 设置里可操作     | ✅ 系统级灰掉       |
| 改系统时间绕过时段     | ❌ 可（有残余）     | ✅ 禁改时间+强制对时   |
| 安全模式 / 恢复出厂   | ❌ 可绕过        | ✅ 系统级禁止       |
| 第三方桌面替换       | ❌ 可设默认       | ✅ 常驻首选桌面      |
| adb 卸载/强停/清数据 | ❌ 可操作        | ✅ 禁调试特性       |

**关键事实（来自项目记忆与 `防护等级与家长须知.md`）：目标机型当前为「非 DO」软管控。**  
这意味着——**下面 7 类绕过里，凡属「防御类」的，在软管控下本质上无法靠 App 代码根治**，只能靠把孩子端设为设备所有者（DO 部署）来锁死。App 在软管控下能做的，是「检测+上报+提高门槛」，而非「阻止」。

> 结论先行：明天上线前，**最高杠杆的动作是部署决策——把出厂/交付的设备默认设为 DO**（已具备 `scripts/do-provisioning.ps1` 与 QR/NFC 方案，见 `DO部署基线引导手册.md`）。代码侧能快速落地的，是补齐下面 §3 的 P0 三项，把「沉默逃逸」变成「可见告警+失效锁定」。

## 一、七大绕过手段可行性分析

### 1. 修改系统时间绕过时长/时段管控

- **现状（较强）**：`TimeProvider`（`core/common/.../TimeProvider.kt`）用单调时钟 `elapsedRealtime` 做护栏，`now()` 对墙钟跳变钳制在 `[anchor, projected]`（L390-414），正常运行中改时间**无法前拨/回拨**；`TamperDetector.detectClockTampering`（L106-178）用墙钟增量 vs 单调增量双源检测并上报 `CLOCK_TAMPERING` HIGH。`TrustedBaseline` 还做了跨重启补偿（L177-205）。
- **残余缺口（非 DO）**：设备**重启后**单调时钟归零，`resumedTrustedMs`（L240-255）会退回用墙钟差估计停机时长——孩子「关机→往前拨 8 小时→开机」可让受信时间向前跳 8 小时，离线期间跳过禁用时段。这是信息论上难根除的边界，但可缓解（见 §3 P1-1）。
- **DO 下**：`setAutoTimeEnforced(true)` + `DISALLOW_CONFIG_DATE_TIME` 直接禁止改时间，从系统层根除（L470-485 / `SelfProtectionModule` L59-60）。

### 2. adb 绕过（卸载 / 强停 / 清数据 / 改设置）

- **现状（仅检测）**：`TamperDetector.detectDebugChannels`（L229-260）检测 `ADB_ENABLED` 并上报 `USB_DEBUG_ENABLED` HIGH；`detectRestrictionLoss`（L300-337）在 DO 下补回 `DISALLOW_DEBUGGING_FEATURES`。
- **缺口**：**Android 无可靠 DPM API 在非 DO 下主动禁用 adb**。非 DO 设备上 `adb shell pm clear/uninstall`、`am force-stop` 全部有效。代码只「上报」不「阻断」。
- **DO 下**：`DISALLOW_DEBUGGING_FEATURES` 由系统强制，adb 无法启用。

### 3. 安装第三方桌面绕过自定义 Launcher

- **现状**：`KioskEnforcer`（L88-92 `setPersistentPreferredLauncher`）+ `LockTaskSupport`（L36-39）在 DO/PO 下把自家 Launcher 常驻为默认并锁定任务。
- **缺口（非 DO）**：`setPersistentPreferredLauncher` 需 DO/PO 权限，**非 DO 下孩子可安装任意桌面并在 HOME 选择器中设为默认**，自家 Launcher 被绕过；`AppHider.isDefaultHome()`（L104-110）能感知但无法阻止。
- **DO 下**：系统级锁定，第三方桌面无法设为默认。

### 4. 停止 WorkBuddy（GuardService）守护进程

- **现状（较强）**：双进程 `:daemon` + `GuardWatchdogService`（JobService 一次性自唤起，L72-106）+"START_STICKY" 前台服务 + 开机广播 `BootReceiver`。
- **缺口（非 DO）**：非 DO 下「设置→强停」会同时杀掉 GuardService、Watchdog、无障碍，**整个守护链一起死**，且孩子无需 root。Watchdog 与主体同 UID，无法互相拉活后被系统一起回收。
- **DO 下**：强停按钮被系统灰掉，无法操作。

### 5. 清除应用数据

- **现状（高危缺口）**：凭据与配置存于 Jetpack **DataStore**（`padguard_auth`/`padguard_config`，`DataModule.kt` L72-73）；策略快照 `AppGuardPolicyStore.cache` 亦源自 DataStore/DB。
- **缺口**：**「设置→清除数据」会同时抹掉 hmacSecret 与本地缓存策略 → 本地时长/应用管控瞬间全部失效**，且因 hmacSecret 丢失，设备也无法再校验服务端指令，必须重新绑定。当前表现是「沉默逃逸」——孩子清完数据即脱管，家长端只看到「离线/不响应」，不会立即意识到是被清数据绕过。
- **DO 下**：清除数据按钮被系统灰掉（同强停）。

### 6. 网络代理 / MITM

- **现状（弱）**：**全仓无任何代理/VPN 主动检测**（grep `HTTP_PROXY`/`VPN`/`ProxyInfo` 零业务代码命中）。传输依赖 Nginx TLS 终止 + `EndpointSafety` 拒绝公网明文（L129-205），但信任系统 CA。
- **缺口**：具备自定义 CA 的主动中间人（如 Fiddler/Charles 导入证书）可解密流量、观察指令与上报内容。由于指令有 HMAC 签名，内容**无法被篡改**，但**明文内容可见**（隐私泄露 + 行为画像）。

### 7. 抓包篡改指令

- **现状（较强）**：指令通道三层门（`CommandGate.kt`）：
  1. 时效：`CommandFreshness` 封顶 15min（L40），`expiresAt` 未签名也改不了寿命；
  2. 签名：HMAC-SHA256（`CommandGate` L63-80），密钥为**每设备独立、服务端下发、Keystore 加密存储**（`AuthRepository` L165-226），**非硬编码全局密钥**；
  3. 幂等：`msgId` 去重（L84）。  
     上行数据同样 HMAC 签名（`UplinkSigner`）。签名失败上报 `INVALID_SIGNATURE` HIGH。
- **缺口**：**无证书固定（CertificatePinner）**（全仓零调用）。主动 MITM 替换服务端证书后，虽不能伪造指令（无 hmacSecret），但可**拦截/重放/观测**；若攻击者从已 root 设备提取 hmacSecret，则可完全伪造指令。此外 `CommandGate` 在 `secret.isBlank() && debug && mock` 时跳过验签（L65-74）——仅调试联调路径，生产 release 不受影响，但需确认发布包 `useMock=false`。

## 二、权限 / 接口 / 传输 专项发现

- **服务端鉴权（较强）**：三态 JWT（家长/孩子/管理员）均写入 `tokenVersion` 支持登出吊销（`JwtTokenProvider`）；`DeviceOwnershipGuard.requireOwned()` 为设备归属唯一入口防 IDOR（`Interceptors.kt`、`WebConfig.kt` L51-121）。未发现越权/未鉴权业务接口。
- **未鉴权白名单需复核**（低成本核查项）：`WebConfig.kt` 排除 `/v1/files/**`、`/v1/server/info`、`/v1/billing/notify`、`/v1/ws`。其中 `/v1/files/**` 有 `FileAccessInterceptor` 软鉴权、`/v1/billing/notify` 为支付回调（应按来源 IP/签名校验而非 token）、`/v1/server/info` 应仅返回非敏感信息。**上线前请逐一确认这 4 个排除项不泄露敏感数据。**
- **明文传输敏感指令**：指令完整性靠 HMAC 保，但**机密性仅依赖 TLS**。无证书固定时，MITM 可见策略明文（见 §1-6/7）。建议 P0 加证书固定补机密性。
- **命令签名 legacy 兼容回退**（`CommandGate.verifySignature` L101-112）：兼容旧 canonical 格式是为版本错峰，一个周期后应删除旧格式分支，缩小攻击面。

| ---- | --------------------------- | -------------------- | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0-1 | **证书固定（CertificatePinner）** | 6 网络代理 / 7 抓包篡改 / 明文 | ~40 行 | 对 API(HTTPS) 与 MQTT(SSL) 端点 pin 生产证书/公钥；私有化 CA 场景保留注入位。直接消除「自定义 CA 主动 MITM」这一类高危观察与重放。OkHttp `certificatePinner` + MQTT `SSLContext` 初始化处加。                 |

## 四、一句话风险结论

- **已较强（不必今晚动）**：指令 HMAC 签名+时效+幂等、受信时钟运行时护栏、双进程守护、DO 下的系统级锁死、服务端鉴权与归属守卫。
- **今晚该补的高危缺口（P0）**：① 证书固定缺失（MITM 可见/可重放）② 清数据「沉默逃逸」未失效锁定 ③ 无代理/VPN 检测 ④ 发布包 mock 开关复核。
- **软管控的本质限制**：在「非 DO」交付态下，强停/清数据/卸载/改时间/第三方桌面/adp 属系统级可操作，App 只能检测上报；**真正治本是把设备设为 DO**——这是明天上线前最该拍板的部署决策。

### 运维补充（P0-1 静态 pin 启用方式，可选）
默认走 TOFU 兜底（首次可信握手记下公钥），已能阻断"未知签发者"的主动 MITM。
如需更稳的静态固定（证书轮换时同步更新即可），运维取生产证书 SPKI 哈希后注入：
```bash
# 取 leaf 证书 SPKI SHA-256（base64）
echo | openssl s_client -connect <域名>:443 2>/dev/null | openssl x509 -pubkey -noout \
  | openssl pkey -pubin -outform der 2>/dev/null | openssl dgst -sha256 -binary \
  | openssl enc -base64
# 打包时注入（多个用逗号分隔）
./gradlew :app:assembleRelease -PcertPins=sha256/<上面输出的base64>
```

## 八、家长端对称加固：证书固定（P0-1 延伸，2026-11-11 续）

### 背景与缺口
P0-1 已对孩子端（`护航成长`）的 HTTPS API 与 MQTT 做了**证书固定（Certificate Pinning）**，阻断"导入自定义 CA 的主动 MITM"解密观测。
但家长端（**护航控制端**）同样连同一个服务端（HTTPS REST + WSS 推送），其 `NetworkModule` 的 OkHttp / WebSocket 客户端**此前未做任何证书固定**——
仅由 `EndpointSafety` 在 URL 层面强制"公网必须 HTTPS"，链路层仍未锁死对端证书。具备自定义 CA 的主动 MITM 虽无法伪造指令（HMAC 保完整性），
却可观测明文行为画像。这是与 P0-1 对称的 MITM 缺口。

### 关键约束（与家长端形态匹配，避免误伤 LAN 部署）
- 家长端地址**运行时可改**（登录页「⚙ 高级设置」、LAN 私有化部署），无法在构建期预知对端证书 → **不能**用静态 pin 硬绑。
- 因此默认走 **TOFU（Trust-On-First-Use）**：首次成功握手记下证书 SPKI；同签发者轮换自动重新记录；陌生签发者出现即拒绝（疑似 MITM）。
- 系统 CA 校验始终先生效：随机/过期/自签证书先被拒，固定逻辑只兜底"合法证书被替换"这一类，故**不会误伤正常公网证书**，
  也**不会破坏 LAN 内网的 http 明文链路**（TLS 不参与，TrustManager 不触发）。
- 运维可用 `-PcertPins=sha256/xxx,sha256/yyy` 注入生产证书 SPKI 哈希，切换为**严格静态固定**（最稳）。

### 10.4 生产环境启用严格静态证书固定（运维命令）
- **孩子端 release 注入**（路径多一段 `/api/v1/`）：
  ```bash
  ./gradlew :app:assembleRelease \
    -PBASE_URL=https://<域名>/api/v1/ \
    -PMQTT_BROKER=ssl://<域名>:8883 \
    -PcertPins=sha256/<leafSPKI>,sha256/<issuerSPKI>
  ```
- **家长端 release 注入**：
  ```bash
  ./gradlew :app:assembleRelease \
    -PcertPins=sha256/<leafSPKI>,sha256/<issuerSPKI>
  ```
- **取 leaf 证书 SPKI SHA-256（服务端/网关侧操作）**：
  ```bash
  openssl s_client -connect <域名>:443 2>/dev/null | \
    openssl x509 -pubkey -noout | openssl pkey -pubin -outform DER | \
    openssl dgst -sha256 -binary | openssl base64
  ```
- 注入后 `BuildConfig.CERT_PINS` 非空 → `CertPinTrustManager` 走**静态 pin**分支，TOFU 不再生效，消除首绑风险。
- 未注入（默认空）：两端均回落 TOFU，适合 LAN/动态地址的内网私有化部署，不阻断正常轮换。
