## 三、本轮发现并修复的缺陷

### D-01（P1，已修复并部署）实时看屏每 10 分钟被掐断，且每次打一条 ERROR + 30 行堆栈

- **现象**：`server_restart.log` 中 10 条 `GlobalExceptionHandler : unhandled exception (response already committed)`，堆栈均为 `AsyncRequestTimeoutException ← TimeoutCallableProcessingInterceptor`，间隔精确 10 分钟，且每条后面紧跟 `stream subscriber added`（客户端重连）。
- **根因**：`ParentStreamController.live` 用 `StreamingResponseBody` 输出无限流，受 `spring.mvc.async.request-timeout=600000` 约束；到点后 Spring 抛异步超时异常。此时响应早已提交（帧一直在写），异常落到 `handleOther` 的"已提交"分支 → 记 ERROR + 全堆栈，并放弃改写响应。
- **影响**：① 家长端看屏每 10 分钟强制断流一次，靠客户端重连兜住，表现为周期性闪"连接中"；② 生产上每 10 分钟一条 ERROR，会把错误率告警打成假阳性，也会掩埋真正的异常。
- **修复**（`Core.kt`、`application.yml`）：
  1. 新增 `@ExceptionHandler(AsyncRequestTimeoutException::class)`：响应已提交 → 只 `log.debug` 一行并返回 null；未提交 → 返回 503（与 Spring 默认语义一致，长轮询有自身 `DeferredResult` 超时，实际不会走到这里）。
  2. 异步超时 10 分钟 → **30 分钟**。不设为无限是刻意的：这条超时同时是"对端掉线但无 FIN"的半死连接回收器；流本身另有"设备 30s 无帧即收流"和"写失败即终止"两条自保护。
  3. 启动参数同步改正（运行实例显式传了 `--spring.mvc.async.request-timeout=600000`，会覆盖 yml，只改配置文件不生效——这是本次排查中踩到的坑）。
- **验证**：新增 2 例单测（已提交→null 且不记 ERROR；未提交→503），`GlobalExceptionHandlerTest` 17 例全绿；服务端全量 472 例 0 失败；重新 `bootJar` → 替 `deploy/app.jar`（旧包备份 `/tmp/app.jar.bak-1657`）→ 重启（PID 7404，`/health` UP/ready/db UP，启动 11.8s）；重启后日志 **0 条 ERROR**，家长端与孩子端 30s 内自动重连，**401 计数 0**。

### D-02（P2，已修复）WS 传输异常日志丢失类型，现场只有一行 `null`

- **现象**：日志出现 `WS transport error: null`（今日 2 次），无法区分"手机断网"与"服务端 NPE"。
- **根因**：`DeviceWebSocketHandler.handleTransportError` 只拼接 `exception.message`，而 NPE 与部分 IOException 的 message 就是 null。
- **修复**：改为输出「异常简单类名 + 非空消息或 `(no message)` + sessionId」，**刻意不打堆栈**——移动端掉线是高频事件，打堆栈会把日志刷爆；需要细节时按 sessionId 关联即可。
- **验证**：编译通过，随全量测试与重启生效。

## 四、真机运行态评估（重要：能力边界的现场证据）

孩子端 `PolicyEngine` 在真机日志中明确上报 **13 项能力因非 Device Owner 而降级**，原文摘录：

```
security.antiUninstall: 需要 Device Owner / Profile Owner
security.antiForceStop: 需要 Device Owner / Profile Owner（降级后进程可被强行停止，仅能靠开机自启与心跳超时告警兜底）
security.antiClockTamper: 无管控权限（时长统计仍基于单调时钟不受影响，但日切与时段判定可能被改时间影响）
security.blockReset: 需要 Device Owner / Profile Owner
security.accessibilityWhitelist: 需要 Device Owner / Profile Owner
peripheral.*: 当前为 LEGACY，无法下发用户限制，外设管控整体不可用
systemLock.autoTime: 需要 Device Owner，当前无法阻止手改系统时间，时段管控可被绕过
systemLock.*: 需要 Device Owner / Profile Owner，系统设置锁定整体不可用
app.installPolicy: 需要 Device Owner / Profile Owner
```

**产品结论（需要产品/运营侧同步给家长）**：在非 DO 的平板上，"改系统时间绕过时段管控"是当前真实存在的绕过路径；计时本身不受影响（单调钟），但"几点该锁"的判定会受影响。这一点必须在《家长须知》与首装引导里明示，并把 DO 引导前置为强推荐，而不是可选步骤。

其他运行态发现：

1. **孩子端安装包落后一版**：设备上是 1.0.4（11:49），而 `D:/builds/padguard/app/outputs/apk/debug/app-debug.apk` 已是 12:41 的加固包（含 Android 14 投影 consent 保活、a11y 开流优先级、授权节流）。**用户报的"看屏授权反复丢失"必须装上这一版才会改善。** 本轮未擅自安装：设备当前处于锁屏管控态，EMUI 安装需要解锁并人工确认（此前已出现 `InstallStaging` 卡死）。
2. **未启用设备管理员**：`dumpsys device_policy` 显示 Enabled Device Admins 为空，与应用自报的"软管控"一致。
3. **未申请电池优化白名单**：属**有意的合规取舍**（`PermissionGuideScreen` 明确注释，受应用商店家庭政策限制），不是缺陷；代价是 EMUI 后台清理风险，需靠前台服务 + 双进程 + 心跳兜底。
4. **孩子端主进程 PSS 126MB 偏高**（daemon 另 20MB）：Compose + 地图 + 图像缓冲合计所致，暂不构成故障，建议纳入观察（见 O-3）。

### 5.2 强项

- **离线优先的落地不是口号**：时间/应用管控在端上有独立判定链（`PolicyEngine` → `AppGuardPolicyStore` → 无障碍顶回），服务端只负责下发；离线队列统一 `JsonLinesFile`（原子覆盖 + 坏行自愈 + 读失败不当空队列）。
- **契约有守卫**：`CommandContractCoverageTest`（指令 × 键 × feature）、`AlertTitleCoverageTest`、`ChildEndpointBoundaryTest` 把跨端协议钉在测试里，改协议会红。
- **错误码分域严格**：孩子端 40xxx / 家长端 1xxx，`Audience` 贯穿异常处理器与信封，避免"孩子端收到家长信封解析失败"这类串台。
- **安全纵深**：JWT + BCrypt + RBAC + 指令 HMAC + WS 运行期账号复核 + 文件归属判定，且吊销点成对处理。

### 5.3 结构性风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 本地 H2 与生产 PG 不同源 | 实体加列靠本地 `ddl-auto=update` 掩盖，生产 `ddl-auto=none` 必炸（已发生一次：`UsageSession` 两列） | 把"加列必须补 Flyway"写进 PR 模板；CI 上用 PG 容器跑一次全量迁移 |
| 测试与开发共享 `uploads/`、`data/` | 全量测试会用测试库随机口令覆盖口令文件，已导致两次"照文件也登不上" | 给测试上下文隔离 `uploads/` 与 `data/`（`@DynamicPropertySource` 指到 `build/test-uploads`） |
| 大量真机用例靠人肉执行 | B-05/B-07/S-05 等跨进程用例只能真机验，回归成本高 | 逐步用 `adb shell am instrument` + 模拟广播/杀进程做半自动化 |
| 单副本约束未写进部署文档首页 | 在线态、看屏会话、告警去重、绑定锁都是进程内状态 | 部署文档置顶"禁止多副本"；扩容前先上分布式锁 |

## 六、优化建议（未实施，按收益排序）

## 九、后续加固：单次限额的「Home 键绕过」与「重启续杯」（同日追加）

上一轮把「应用单次限额只在内存、重启即刷新」列为未修复候选。深入代码后发现问题比记录的更严重：
**不需要重启，按一下 Home 再点回来就能把计时清零。**

### 根因

`AppLimitEnforcer` 用「本次前台会话的起始单调点」做减法：

```kotlin
if (foregroundPackage != lastForegroundPackage) {
    sessionStartElapsed = nowElapsed      // ← 每次前台变化都重置
}
...
val sessionMs = nowElapsed - sessionStartElapsed
```

两个后果：

| 绕过手法 | 成本 | 结果 |
|---|---|---|
| 按 Home → 立刻点回应用 | 2 秒 | 单次计时归零，`singleMinutes` 永远达不到 |
| 重启设备 / 进程被回收 | 一次重启 | `resetSampling()` 同样清零 |

即「每次最多玩 30 分钟」在真机上等价于不存在。这属于**离线核心红线**（时间/应用管控必须本地独立生效）内的失效。

### 修复方案：累计 + 休息阈值 + 落盘

1. **改为累计量**：`SingleSession.accumulatedMs` 由每轮采样的 delta 累加，不再用「现在 - 起点」。
2. **休息阈值 5 分钟**（`SINGLE_SESSION_REST_MS`）：离开该应用不满 5 分钟就回来 → **续算**；
   满 5 分钟才算真的休息过，重新起表。秒切不再获得新额度，20 分钟护眼休息则正常算休息。
3. **多应用会话表**（上限 4 条）：只留一个槽位时，切到桌面会把上一个应用的累计覆盖掉 ——
   等于绕过照旧。表让「短暂离开再回来」能续算，容量有界不会随安装量膨胀。
4. **跨进程落盘**：`SingleSessionStore`（engine 纯接口）+
   `PrefsSingleSessionStore`（app 实现，`padguard_session` 单键 `putStringSet` 原子写）。
   恢复时按「离开时长」决定续算还是重开：同一次开机用单调差（改系统时间无效），
   重启过则用受信墙钟差；差值为负按「没离开过」处理（宁可少放行）。
5. **语义拆分**：`resetSampling()`（重开采样，**不清**会话）与 `resetSession()`（清零额度，
   家长「重置策略」调用）分开 —— 早期合成一个，正是「开机顺带清零」的来源。

### 顺带修掉的两处

- `sessions` 必须是并发容器：`track()` 在采样协程、`evaluate()` 在锁屏页 UI 线程都会读它，
  普通 `LinkedHashMap` 会在「息屏结算」与「倒计时刷新」并发时抛 `ConcurrentModificationException`，
  异常落进 `runSafely` 就是「这一轮管控没跑」。
- 熄屏/护眼休息的「结算」只做**一次**（`wasScreenOn` / `wasEyeCareResting` 跳变标志）。
  每轮都结算的话，休息结束那一刻 `touch` 还是「刚才」，20 分钟休息被判成「没休息过」。

## 十、第十八轮：把「能玩 15 秒」和「白送额度」两个真实窗口收掉（同日追加）

### D-04 孩子点开「额度已用完」的应用，还能玩最多 15 秒

**现象**：家长端显示"今日已用完"，孩子点开该应用却能正常玩，直到下一个采样点才被顶回。

**根因**：所有限额判定只发生在 `GuardService` 主循环的 `doTick` 里，而主循环是
`delay(MIN_TICK_MS)` 即 **15 秒一轮**。窗口切换那一刻系统里没有任何判定，
弱网把主循环拖慢时这个窗口还会更长（长轮询串行在同一个循环里）。

**修复**：加一条"前台切换即唤醒"的旁路，但**不复制判定逻辑**：

| 位置 | 做什么 | 为什么在这里 |
|---|---|---|
| `OperationGuardAccessibilityService` | 收到 `TYPE_WINDOW_STATE_CHANGED` 且包名真的变了 → 发唤醒信号，并在 1.5 秒后补发一次 | 它是唯一能在窗口切换**那一刻**知道新前台是谁的组件 |
| `GuardTickSignal`（新增） | `Channel(CONFLATED)` + 1 秒节流 + `awaitWithin(timeout)` | 信号不等于广播：主循环只关心"有没有被叫醒"；节流防孩子连点五个图标触发五次完整采样 |
| `GuardService` 主循环 | `delay(15s)` → `tickSignal.awaitWithin(15s)` | 判定仍只在 `PolicyEngine.tick` 一处执行，口径不分叉 |

**为什么要补发一次**：`ForegroundAppMonitor` 走 `UsageStatsManager.queryEvents`，
刚发生的 `ACTIVITY_RESUMED` 有几秒写延迟；窗口内查不到事件时它**沿用上一次结果**
（`lastKnown`），所以"立刻那一轮"很可能仍解析出旧前台、判定落空。
1.5 秒后的补发把这条竞态盖住，且每次切换只保留最新一个补发任务（`tickFollowUpJob` 先 cancel）。

**为什么不能直接信无障碍给的包名**：无障碍事件包含 toast/对话框等非前台窗口的包名，
拿它当"计时归属"会把使用时长记到错误的应用上。所以它只负责"叫醒"，判定仍由 tick 采样。

**顺带**：`awaitWithin` 必须带超时——漏一个信号只能退化成原来的 15 秒节奏，
绝不能让主循环永久挂起（那比 15 秒延迟严重得多）。这条性质由单测钉死。

### D-05 采样增量被截断成 60 秒：深睡多记、卡顿少记

**根因**：`computeDelta` 直接用 `elapsedRealtime` 差值再 `coerceAtMost(60_000)`。

- 深睡 8 小时：差值巨大 → 被截断成 1 分钟 → **每次睡眠白记 1 分钟**；
- 主循环被弱网/GC 拖住 3 分钟：差值 3 分钟 → 被截断成 1 分钟 → **少记 2 分钟，等于白送额度**。
  这条正是待办里"弱网使采样 >60s 被 MAX_DELTA 截断少算"，方向对孩子有利，所以一直没被投诉。

**修复**：改用**两个单调钟取小**：

```kotlin
delta = min(now.elapsedRealtime - last.elapsedRealtime,   // 含深睡
            now.uptimeMillis    - last.uptimeMillis)       // 不含深睡
```

物理含义就是"这段时间设备真的醒着多久"：深睡时第二个差值不动 → 取 0；
主循环卡顿时两个同步前进 → 全额计入。`MAX_DELTA_MS` 从 60 秒抬到 **10 分钟**，
只作脏值/病态卡顿的防御性上限，不再承担"排除深睡"的职责。

**护眼计时（EyeCareEnforcer）不能用同一把尺子**，它要的是两个不同的量：

| 用途 | 用的钟 | 理由 |
|---|---|---|
| 连续用眼累计 | `min(含深睡, 不含深睡)` | 睡着的 8 小时不算用眼；卡顿的 3 分钟要算 |
| 息屏是否构成"有效休息" | **真实流逝（含深睡）** | 睡一夜当然算休息过 |

后者原本也被截断到 60 秒，导致一个很具体的坏体验：**孩子白天连着用了 35 分钟
（阈值 40），睡一夜后早上解锁用 5 分钟就被强制休息锁屏** —— 因为"夜里只休息了 1 分钟"。

## 二、`devices.entitlement_state` 没有 Flyway 迁移（P0，已修）

### 怎么发现的
H2 的 `data/padguard.trace.db` 每次启动都多一段堆栈：

```
alter table if exists devices alter column entitlement_state set data type varchar(20) default 'ACTIVE'
→ JdbcSQLSyntaxErrorException [42000-224]
```

顺着查下去发现两件事：

1. `Device.entitlementState` 用的是 `columnDefinition = "varchar(20) default 'ACTIVE'"`，
   Hibernate 在 H2 上每次启动都想"补默认值"，而 H2 2.x **不支持**「改类型 + 带 DEFAULT」的组合语法
   → 每次启动堆一段堆栈进 trace.db，真故障反而被噪音淹没。
2. 更严重的是：**这条列没有任何 Flyway 迁移**。生产 Postgres 跑 `ddl-auto=none`，
   列只由 Flyway 创建 —— 也就是说生产库 `devices` 表根本没有 `entitlement_state` 列，
   而 `Device` 是每个孩子端接口都要加载的实体，`SELECT devices` 会直接抛
   "column does not exist"，家长端设备列表 / 心跳 / 策略下发 / 绑定解绑**全线 500**。
   这与上一轮 `usage_session` 的 rest 列（V2026110702）是同一类坑。

顺手做了一次**全量对账**：把 `Models.kt` + `ExtraModels.kt` 里所有 `@Column(name=...)`
与全部迁移脚本的文本比对，**只有这一列缺失**，其余 100% 覆盖。

### 修复
- 新增 `V2026110703__device_entitlement_state.sql`：
  `ADD COLUMN IF NOT EXISTS entitlement_state VARCHAR(20) DEFAULT 'ACTIVE'` +
  `UPDATE ... WHERE entitlement_state IS NULL`（存量行兜底，因为 Kotlin 侧是非空 String，
  读出 NULL 会直接抛异常）。
- 实体改为 `@Column(name = "entitlement_state", length = 20)`，**去掉 DDL 里的默认值**，
  并保留 `length = 20`（不写会被当成 varchar(255)，Hibernate 又会反复尝试加宽列）。
  默认值改由「迁移 DDL + Kotlin 初值」两处保证。

### 证据
重启后 `data/padguard.trace.db` 的最后写入时间停在修复前（17:44），新一次启动（17:50）
**没有再追加任何记录**；`/health` `db=UP`。

# 第二十轮：`uploads/` 磁盘孤儿清扫（含口令文件防误删）—— 2026-11-07 19:20–20:00

## 一、问题：保留期清理扫不到"从来不入库"的文件

`RetentionCleanup` 有四步清理（定位轨迹、截图、媒体任务、设备上传文件），**每一步都以
数据库记录为起点**（"查到记录 → 按记录的路径删文件"）。这在设计上没错，但它意味着：

> **记录不存在时，磁盘上的文件永远不会被扫到。**

于是有三条稳定的孤儿产生路径，都不报错、不告警：

| 路径 | 怎么产生 |
|---|---|
| 写盘成功、落库失败 | `storeDetailed` 先 `writeBytes` 再 `save`：save 抛异常或进程被 kill → 文件留下、记录没有 |
| 历史绝对路径 | 早期版本把 `storedPath` 存成绝对路径，目录搬家后 `resolve()` 全失效、记录被人工清掉 |
| 测试/手工写入 | 集成测试与 curl 直接把样本文件写进 `storageDir`，从不进库 |

本机实测：跑过多轮集成测试后 `uploads/` 里躺着 **419 个从不入库的样本文件**
（`shell.php.png`、`evil.png`、`big.png`…）。危害不止占磁盘 —— `maintain.ps1`
会把整个 `uploads/` 复制进发布包，**这些测试载荷会随包分发给家庭用户**。

## 二、修法：新增"磁盘孤儿"清扫（而不是改保留期清理）

`FileStorageService.deleteOrphanFiles(graceDays, maxDelete, dryRun, protectedNames)`
反向扫描：列目录 → 拿"库里登记过的文件名集合"比对 → 无记录 + 超过宽限期 → 删除。

安全边界（这一条链路的失效后果是**不可逆删除**，所以每条都对应一个真实的误删路径）：

| 边界 | 挡住什么 |
|---|---|
| **读库失败返回 `dbReadFailed`，一个都不删** | 空集合会被理解成"所有文件都没登记" → 一次数据库抖动删空整个 `uploads/`（与离线队列 `readOrNull()==null` 同一类坑） |
| 只删 mtime 早于 **7 天**的文件 | 写盘→落库之间的竞态窗口；库从旧备份恢复导致"文件比记录新" |
| 宽限期**强制 ≥1 天**（传 0 也夹到 1） | 调用方/后台参数写成 0 就等于关掉上面那条保护 |
| 只比对**文件名**，不比路径 | 历史绝对路径记录（`/opt/padguard/uploads/x.png`）会被误判成孤儿 → 升级即批量误删 |
| 只处理根目录普通文件，不递归 | 子目录可能是挂载进来的别的东西 |
| 单次删除上限 5000，并回报 `truncated` | `storage.dir` 配错指向别的图片目录时，最多也只删这么多 |

### 踩到并堵上的关键误伤：两个初始口令文件

`uploads/` 根目录下还躺着 `管理员初始密码-请登录后修改.txt` 与 `初始密码-请登录后修改.txt`
—— 它们**不在数据库里**，按"无记录即孤儿"的规则会被删掉。而这两个文件是管理员/家长
口令被随机重置后**唯一的取回入口**（本机 11-07 已因口令不一致踩过一次登录锁死）。
所以保护名单收在**存储层**（`FileStorageService` 的构造参数，与两个 Initializer 用同一组
配置键），而不是让每个调用方自己传：漏传的代价就是把运维关在门外。

## 三、可达性：定时 + 后台手动

- 定时：`RetentionCleanup.sweepOrphanFilesDaily()`，每日 **05:10**
  （错开 04:00 / 04:30 两个清理任务，不抢同一分钟的磁盘 IO）；读库失败打 **error**（静默跳过会让孤儿无限堆积）。

# 第二十一轮：响应压缩 + 应用层安全头（含一个被测试逼出来的真 bug）—— 2026-11-07 20:05–20:35

## 一、为什么做这一轮

前二十轮都在修"功能/安全/一致性"缺陷，**传输层从来没被算过账**。这次盘了一遍：

- `application.yml` 与 `nginx/nginx.conf` 里都没有任何 `gzip` / `compression` 配置 ——
  也就是说**所有 JSON 响应、后台全部 JS/CSS 都是明文原样传**。
- `nginx.conf` 有 `X-Content-Type-Options` / `X-Frame-Options` / HSTS，但那套配置**只在
  docker + TLS 反代形态生效**；家庭部署的实际形态是家长端直接填 `http://<内网IP>:8090`，
  请求根本不过 nginx，**三层头一个都没有**。
- `FilesController` 在注释里写"配合 nginx 的 nosniff 双保险"，而它自己的下载响应确实设了
  nosniff —— 其余所有响应（含后台 HTML、错误页）没有。

## 二、改动

### 1. 响应压缩（`server.compression`）

```yaml
server:
  compression:
    enabled: true
    mime-types: application/json,application/xml,text/html,text/plain,text/css,application/javascript,text/javascript
    min-response-size: 1024
```

两个刻意的取舍：

- 白名单**只列文本**。`application/octet-stream` / `image/*` / `video/*` 一律不列：
  截图、录屏、APK 本体已是压缩格式，再过一遍 gzip 只烧 CPU、体积反降不下去。
  `text/event-stream` 也不列 —— 压缩要攒缓冲，会把实时流变成"憋一坨再发"。
- **只在应用层做一层**，nginx 不重复配。两层都开时 nginx 看到上游 `Content-Encoding: gzip`
  会跳过，等于白留一份随时会漂移的配置；而 LAN 直连形态根本不过 nginx。

客户端零改动：OkHttp 与浏览器默认都发 `Accept-Encoding: gzip` 并透明解压，两端代码里
也没有任何 `Accept-Encoding` / `contentLength()` 依赖（已 grep 确认）。

### 2. 应用层安全响应头（`SecurityHeaders` + `ResponseHeaderFilter`）

`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: no-referrer`，
用 `OncePerRequestFilter` 覆盖**全部**请求（拦截器管不到 404、`/admin/` 静态资源与被排除鉴权的路径，
而这三类恰好是上述风险的主要载体）。

### 3. 测试逼出来的真 bug：错误响应把安全头全丢了

写 `security headers survive error responses`（断言 401 响应带头）时直接红：
`expected:<nosniff> but was:<null>`。根因在 `GlobalExceptionHandler.resetIfPossible`：

> 写 JSON 错误体前会 `response.reset()`（为清掉 controller 预设的 `Content-Type`，
> 否则 "没有转换器能用 APK 类型写 ApiResponse"）。而 `reset()` **连全部响应头一起清空**。

也就是说：**最需要 nosniff 的错误响应（最容易被嗅探成 HTML、被 iframe 套）恰恰是唯一没有它的那一类**。
修法是 `reset()` 成功后按同一份定义补回（`SecurityHeaders.apply(response)`），
常量与过滤器共用一份，不再两处各写一遍字符串。

## 三、实测（本机 home / 8090，同一进程前后对比）

静态资源（`/admin/` 由 Spring `ResourceHandler` 从 `padguard-admin/` 目录直出）：

| 资源 | 未压缩 | gzip | 降幅 |
|---|---|---|---|
| `assets/js/api.js` | 31,749 B | 11,088 B | −65% |
| `assets/css/app.css` | 16,713 B | 3,763 B | −77% |
| `index.html` | 6,470 B | 2,773 B | −57% |
| **后台全部 17 个 js/css/html** | **218,156 B** | **80,438 B** | **−63%** |

响应头（`curl -D -`）：

```
GET /admin/assets/js/api.js  → X-Content-Type-Options / X-Frame-Options / Referrer-Policy 三个都在
GET /health                  → 三个头都在
GET /v1/devices (401)        → 三个头都在   ← 修复前为 null
GET /v1/nope    (404)        → 三个头都在
```

# 第二十三轮：孩子端运行期地址校验（U-06/07 的下半场，下沉 EndpointSafety）—— 2026-11-07 21:40–22:20

## 一、问题（上一轮明确标注的待办）

上一轮把孩子端**构建期**出厂地址守卫补齐了，但留了一个被测试逼出来的真缺口：

> 孩子端**无运行期地址校验**（家长端有 `EndpointSafety`）：手输公网 `http://IP:8090` 仍会明文发令牌。

具体风险链：孩子端 `AndroidManifest` 全局 `usesCleartextTraffic="true"`（家庭内网私有化部署必须），
「高级设置」允许运行时把地址改成任意 host。家长端早有 `data/remote/EndpointSafety.kt` 在保存地址时
拦截公网明文；孩子端只有 `TransportSettings.normalizeBaseUrl`（仅补尾斜杠），**没有任何安全准入** ——
只要有人往孩子端「高级设置」里手填一个公网 `http://`，登录令牌、孩子的位置/截屏/使用记录就明文过公网。

## 二、改动

### 1. 共用传输层新增 `EndpointSafety`（`core/transport`，JVM 可单测）
下沉家长端的设计，落到**共用的** `core/transport` 模块（两端都依赖它），所有写入地址的代码都经过它：

- `check(raw, allowCleartextPublic=false): Verdict` —— HTTP baseUrl 准入：
  https 放行；http + 回环/私网（10/172.16~31/192.168/127/169.254 及对应 IPv6）放行并标记 `LAN_CLEARTEXT`；
  公网 http 拒绝（除非显式 `allowCleartextPublic`）；域名形式 http 一律拒绝（保守）；
  userinfo / query / fragment 拒绝；根路径自愈补 `/api/v1/`（孩子端接口前缀）。
- `checkMqtt(raw, allowCleartextPublic=false): Verdict` —— MQ broker URI 准入（**新增的对称防线**）：
  `ssl://`/`tls://`/`wss://` 放行；`tcp://`/`ws://` + 内网放行；公网明文拒绝（除非显式开关）；
  缺 scheme / 未知 scheme / 带 userinfo 拒绝。broker URI 是 `tcp://host:port` 形态，OkHttp 的
  `toHttpUrlOrNull` 不认，故单独解析。
- `isLanHost(host)` 与家长端同算法（严格点分十进制，非标准形式一律按非私网拒绝）。

### 2. 唯一写入点 `TransportSettings` 强制闸门
- `setBaseUrl` / `setMqttBroker` 改为先过校验，**拒绝的地址不落盘、仅记日志并返回 `Verdict`**；
- 启动时从存储读出旧值也过校验，不安全的旧值直接丢弃并回退到构建期默认值；
- 读取 `core/transport` 自己的 `BuildConfig.ALLOW_CLEARTEXT_PUBLIC`（默认 `false`）—— 孩子端**默认关死**公网明文；
- 调用点 `RealRemoteDataSource`（绑定响应下发 broker）、`BindViewModel`、`ChildLoginViewModel`、
  `ServerConfigDialog` 全部经过这两道闸门，无第二写入路径。

### 3. 弹窗级即时拦截（`ServerConfigDialog`）
高级设置保存前先 `EndpointSafety.check(built)`，被拒则把原因直接显示成错误文案，不交给底层落盘。
与构建守卫、`setBaseUrl` 三重防御。

## 三、编译踩坑（已解决，值得记一笔）

1. **KDoc 里的 `/*` 会触发"Unclosed comment"**：类注释中写了 `` `tls://*` ``，其中 `//*` 被 Kotlin lexer
   误判为重新打开块注释，导致整个文件到 EOF 都"未闭合"。改为 `tls://` 即解。
2. **嵌套在 `object` 内的 sealed class 的 smart-cast 失效**：`EndpointSafety.Verdict.Allowed/Rejected`
   的成员（`.reason`/`.normalizedUrl`/`.level`）在 `is` 判定后取不到。把 `Level`/`Verdict` **提到文件顶层**
   后解决；调用处一律用顶层 `Verdict`，`EndpointSafety` 只留函数。
3. **`if (x is Rejected) return` 后的控制流 smart-cast 在本场景不传播**（疑似与后续 lambda 捕获相关），
   统一改成 `when (val verdict = ...)` 的每分支显式 smart-cast，编译通过。
