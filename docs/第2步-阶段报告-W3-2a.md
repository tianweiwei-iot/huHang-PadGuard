## 二、治理口径：不替你假设部署形态

`⟦TBD-2⟧`（云 SaaS / 家庭自建 / 双形态）至今未拍板，且仓库内文档与代码互相矛盾。本批**只落实一条与口径无关的技术底线**：

| 场景 | 判定 | 依据 |
|---|---|---|
| `https://` 任意 host | ✅ 放行 | 链路加密 |
| `http://` + 回环 / 私网 IP / `localhost` | ✅ 放行，标记 `LAN_CLEARTEXT` | 家庭/校园内网私有化部署的既定口径，`Manifest` 注释亦如此；一刀切关掉会让内网部署直接连不上 |
| `http://` + 公网 IP / 域名 | ❌ 拒绝 | 无论哪种部署形态，Bearer 令牌与儿童数据走公网明文都不可接受 |
| `http://` + 公网，但走专线/VPN | ⚠️ 需显式 `-PALLOW_CLEARTEXT_PUBLIC=true` | 逃生开关，产物标记 `EXPLICITLY_INSECURE`，要求运维留痕 |

**保守取舍**：域名形式的 http 一律拒绝（含 `.local` mDNS），因为静态判定无法保证域名解析到内网。若学校内网确实用域名且无 TLS，应走 HTTPS 或走显式开关 —— 已列入下方待确认项，未自行假设。

## 五、架构缺陷：两套方案

**A · 低成本快速版（本批采用）**：构建期注入 + 出厂守卫；运行期纯函数准入；HTTP/WS 双通道拦截；存量配置自动迁移；显式逃生开关。优点：不动服务端、不改协议、可立即上线前验证。残余：域名 http 一律拒绝（保守）、`usesCleartextTraffic` 仍全局开启（依赖代码层拦截，若未来新增未走拦截器的网络通道会漏）、https 升级迁移依赖服务端 TLS 已就绪。

**B · 长期重构版**：`networkSecurityConfig` 按域名白名单细粒度放开明文（配合私有 CA / 证书固定），统一配置中心下发服务端地址与证书指纹，Nginx 强制 TLS 1.2+ / HSTS，设备侧 mTLS，端上链路层做证书校验与上报；把「地址安全等级」纳入设备状态上报与运维巡检。适合 `⟦TBD-2⟧` 定型、多租户/多厂商 DPC 立项后一并做。**建议 A 先闭环上线，B 待口径定型后立项。**

## 六、🚩 无法仅靠代码解决（高亮）

1. **TLS 证书与已备案域名**：`nginx/certs/`、`mosquitto/certs/` 仍是空目录；release 现在要求注入 `https://` 地址，但证书签发、域名 ICP 备案、`⟦TBD-2⟧` 部署形态都需外部完成。
2. **服务端 TLS 是否就绪直接决定存量迁移效果**：旧版本用户升级后地址被自动改成 `https://`；若服务端仍未终止 TLS，会连接失败并提示去「高级设置」改地址 —— 这一步必须联调确认。
3. 沿用第一步清单：微信支付商户资质、短信服务商、隐私政策法务复核 + 用户协议 + 儿童个人信息保护规则 + PIPIA、App 备案/软著/上架材料、厂商 DPC 与 Zero-touch 对接、真机 adb、等保范围、72h 值守与灰度家庭招募。
4. **真机验证项（新增）**：旧版 App 升级后地址迁移是否无感、明文公网地址被拒时 UI 是否给出可读原因、WS 通道在内网/HTTPS 下是否正常重连。
