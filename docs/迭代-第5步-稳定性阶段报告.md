## 三、修复计划与改动位置

### 3.1 S-01：`UserSession` 补 `@Table(indexes)`（home 档索引闭环）

**根因**：F-01 新增的 `user_sessions` 表索引写在 Flyway 迁移里（`V2026110902`）。但 `home` / `local` 档 `flyway.enabled: false` + `ddl-auto: update`，表由 Hibernate 自动建，**不会**执行迁移里的 `CREATE INDEX`，于是 home 部署下该表无索引，`revokeAllForUser` / `findByRefreshJtiAndRevokedFalse` 走全表扫描。

**修复**：在实体上声明 JPA 索引，使两档（Flyway / Hibernate ddl-auto）都生成索引：

```kotlin
@Table(
    name = "user_sessions",
    indexes = [
        Index(name = "idx_user_sessions_jti", columnList = "refresh_jti", unique = true),
        Index(name = "idx_user_sessions_user", columnList = "user_id, revoked")
    ]
)
class UserSession(...)
```

- 位置：`domain/ExtraModels.kt`
- docker 档 `ddl-auto: none` 不受影响（索引仍来自迁移，同名不冲突）。

### 3.2 S-02：优雅停机

**修复**：`server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`（见 §3.2 风险取舍）。
- 位置：`application.yml` 顶部 `server:` 与 `spring:` 基块（所有 profile 继承）。

**停机宽限期取舍（两套方案）**：

| 方案 | 描述 | 取舍 |
|---|---|---|
| A（采用） | 宽限期 30s：在途 HTTP 与 `@Scheduled` 在 30s 内自然走完，超时强制回收 | 看屏长连接（异步超时 30min）会在维护期被断开——属预期，不值得为一条流卡 30min 停机 |
| B | 宽限期设 30min 对齐看屏超时 | 部署期间停机最长卡 30min，滚动发布/紧急重启不可接受 |

### 3.3 S-03：HikariCP 显式调优

**修复**：在基块 `spring.datasource.hikari` 下显式配置：

```yaml
hikari:
  pool-name: pg-hikari
  maximum-pool-size: 20
  minimum-idle: 5
  connection-timeout: 30000
  idle-timeout: 600000
  max-lifetime: 1800000
  leak-detection-threshold: 30000
  connection-test-query: SELECT 1
```

- 位置：`application.yml` 基块 `spring.datasource`
- 验证：上下文启动日志已打印 `pg-hikari - Shutdown initiated`，证明参数被读取生效。

### 3.4 S-04：MQTT 停机主动断开

**根因**：`MqttConfig.mqttClient()` 只负责连上，`cleanStart=false` + `automaticReconnect=true`，进程被终止后 Broker 等到 keepalive 超时（90s）才判定掉线；滚动发布期间旧实例僵尸会话堆积。

**修复**：新增 `MqttLifecycle`（实现 `DisposableBean` + `@PreDestroy`）在销毁阶段 `client?.disconnect()`，给 Broker 干净断开信号，会话即时回收；注入的是可空 Bean（MQTT 关闭时返回 null），此时方法体退化为 no-op，不影响免 Broker 部署。
- 位置：新增 `config/MqttLifecycle.kt`

### 3.5 S-05：`resetParentPassword` 事务内不持锁做网络调用

**根因**：原实现 `@Transactional` 内 `findByIdForUpdate`（持 `users` 行锁）后直接 `mailService.sendPasswordReset(...)`（SMTP 网络调用，已设 5s 超时但仍属慢路径），锁在 5s 网络往返期间不释放，并发几次重置即把连接池/行锁排队耗尽。配置文件注释本身已点名此风险。

**修复**：把邮件发送移到事务**提交之后**——用 `TransactionSynchronizationManager.registerSynchronization(afterCommit { ... })`，提交后连接已归还，仅占请求线程；并加 `isSynchronizationActive()` 兜底（脱离事务上下文如纯单测时退回内联发送，避免抛 `IllegalStateException` 中断重置流程）。
- 位置：`service/AdminParentService.kt`（`resetParentPassword`）

## 五、已知限制 / 后续建议（不在本轮范围）

1. **索引不对称性（已知，建议 Step7 收口）**：迁移内 65 条索引在 home 档（`ddl-auto`）不会生成，仅本步为新增 `user_sessions` 补了 `@Table(indexes)`。home 档跑 H2 单家庭规模，顺序扫描可接受；若要 docker 多实例/大数据量对等，建议给其余热实体也补 `@Table(indexes)`。
2. **04:00 `usage_logs` 批量清理**为单事务 `DELETE`（百万行级），仍可能占用 4 线程调度池中的一条；建议改为分片 `DELETE ... LIMIT 1000` 循环 + `REQUIRES_NEW`，与秒级任务隔离。
3. **外部指标导出缺失**：当前为进程内指标（重启清零），单实例 home 部署足够；docker 多实例建议 Step7/8 引入 `micrometer-registry-prometheus` + 鉴权 `/metrics` 端点。
