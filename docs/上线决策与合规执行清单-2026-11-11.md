## 1. Device Owner 决策建议（P0-1 治本项）

### 1.1 现状（代码侧已具备，但受设备能力制约）
- 孩子端已实现 `DeviceOwnerEnforcer.kt`、`core/engine/admin/DeviceAdminBridge.kt`、`ui/lock/LockTaskSupport.kt`（锁任务白名单）、`permission/DeviceAdminRequest.kt`、`ui/profile/ProfileViewModel.kt`（读取 `DevicePolicyManager` 状态）。
- **DO 能补强的能力**：`setPackagesSuspended`（免 root 挂起黑名单应用）、`setLockTaskPackages`（沉浸锁屏）、防止被「设置」里强停/卸载。
- **软管控（默认、非 DO）守不住的项**（来自红线约定）：卸载、强停、「改系统时间」绕过时段判定、安全模式 / 恢复出厂。
- **目标机型约束**：工作记忆记录「目标机型无 DO → 改系统时间可绕过时段管控」，且孩子端设备为华为 EMUI 10（API 29），DO 激活（QR/NFC/ADB `dpm set-device-owner`）在消费级 ROM 上普遍不开放或需解锁。
- **已落地的诚实披露**：家长端「管控能力说明」弹窗（`CapabilityNoticeDialog`）与孩子端「被监管中」提示（`HomeScreen.SupervisedHint`）已上线，明确告知降级边界。

### 1.2 风险矩阵
| 攻击面 | 软管控 | + DO | 结论 |
|---|---|---|---|
| 卸载 / 强停 App | ❌ 守不住 | ✅ | DO 显著降险 |
| 改系统时间绕过「时段」 | ❌（墙钟依赖） | ⚠️ 部分 | 受信钟 A1 已防「日切伪造」，但墙钟时段仍可被拨动 |
| 安全模式 / 恢复出厂 | ❌ | ❌（ROOT 级不可防） | 任何方案都守不住，只能事前提示 |
| 离线本地管控生效 | ✅（不变量已保证） | ✅ | 与 DO 无关，已独立生效 |

### 1.3 选项
- **A. 首版不依赖 DO，诚实披露 + 软管控**：最快上市；接受「非 DO 大比例设备」的降级边界（已用弹窗如实告知）。风险可控、法务边界清晰。
- **B. 渐进式 DO：支持 DO 的设备提供一键激活引导**：检测 `DevicePolicyManager` 能力，对可激活设备弹出「启用更高管控」引导（QR/ADB 步骤），不可激活设备走 A。代码侧 `setPackagesSuspended`/`LockTaskSupport` 已就绪，缺的是**激活引导与能力探测 UI**。
- **C. DPC / Kiosk 整机管控**：仅适用于企业/MDM 发机，消费级不可用，本期不取。

### 1.4 推荐：**A + B 渐进式**
1. 首版按 **A** 上线（已具备诚实披露 + 软管控 + 离线独立生效）。
2. 同期补 **B** 的能力探测与激活引导（见 1.5），作为「渐进增强」而非上线圈门——**不让 DO 成为公开上线的硬阻塞**。
3. 在家长端「管控能力说明」中区分「当前设备已启用/未启用更高管控」，避免一刀切话术。

### 1.5 若采纳 B，具体落地任务（独立于本会话，待拍板）
- [ ] `ProfileViewModel` 暴露 `isDeviceOwnerCapable()`（基于 ROM/Android 版本/已激活状态）。
- [ ] 孩子端「更高管控」引导页：分 EMUI / 原生 Android 给出 QR 或 `adb shell dpm set-device-owner` 文案与一键复制命令。
- [ ] 家长端同步显示该设备 DO 状态；未启用时提示降级边界（复用 `CapabilityNoticeDialog`）。
- [ ] 真机回归新增：DO 激活后 `setPackagesSuspended` 生效、锁任务白名单生效（R 类补两条）。

## 3. 发布与回滚预案

### 3.1 发布流程（门禁 → 构建 → 部署 → 探活 → 灰度）
1. **门禁**：`CI=true bash padguard-server/scripts/launch-preflight.sh` 全绿（三端测试+lint），否则阻断。
2. **构建**：
   - 服务端：`cd padguard-server && ./gradlew bootJar`
   - 孩子端/家长端：`assembleRelease -PBASE_URL=... -PMQTT_BROKER=...`（release 必须注入接入点）
3. **停服→替换→起服**：先停 8090（Windows jar 占用），`cp build/libs/app.jar deploy/app.jar`，再起 java（home 档）。
4. **探活**：`curl http://127.0.0.1:8090/health` 返回 `ready=true`。
5. **灰度**：先小批量家庭（10–20，即「受控内测」），观察 3–7 天无 P0 异常再扩量。

### 3.2 回滚
- **服务端**：保留上一版 `deploy/app.jar` 备份，停服→还原 jar→起服。Flyway 社区版不支持 `undo`，仓库内全部迁移均为单向 `Vxxx__xxx.sql` —— **全库备份 + 回灌是唯一数据库回滚路径**：回滚前必须先跑 `backup-db.sh` 并在演练环境验证备份可恢复；禁止按"迁移文件带 down"的假设制定预案。
- **孩子端/家长端**：应用市场「暂停发布 / 回退上一版本」；已装加固包用户通过热更新策略降级（若有）。
- **数据**：回滚前先 `backup-db.sh` 留快照，确保可回灌。

### 3.3 真机回归（P0-2，硬阻塞，需硬件）
设备仍装 **1.0.4**，加固包需真人装（EMUI 10 装包需解锁+人工确认）。回归清单见 `docs/上线推进清单-2026-11-11.md` §2（R-01~R-11）。**此项是公开上线前必须补齐的最后一环**，本会话无硬件无法代执行。
