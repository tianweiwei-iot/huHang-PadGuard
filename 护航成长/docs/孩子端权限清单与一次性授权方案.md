# 护航成长（孩子端）权限清单与一次性授权方案

> 更新日期：2026-10-07
> 范围：`E:/项目/护航成长`（被管控端）全部功能所需的系统权限、设备身份与用户确认项。
> 结论：**全系统 19 项权限 / 4 类获取方式，已收敛为"一次 App 内确认 + 系统层自动排队引导"**。

---

## 一、结论摘要

| 项目 | 改造前 | 改造后 |
|---|---|---|
| App 内需家长做决定的次数 | 8～10 次 | **1 次**（点「同意并授权」） |
| 装机路径涉及的界面 | 权限引导页 → 登录页 → 绑定页 → DO 门禁 → 主页 + 协议弹窗 + 录屏授权 | 登录页 → **一次性授权页** → 绑定页 → 主页 |
| 是否会出现二次授权 | 会（相机在扫码时才弹、无障碍在做管控时才提示、录屏在主页后才弹） | 不会，装机一次收走全部 |
| 监管 / 上架合规 | 已剔除短信/通话记录/电话状态等高危项 | 不变 |

**必须讲清的一件事**：Android 有四项权限在技术上**不允许 App 代为用户授予**，
连 Device Owner 都不行。"一次确认"指的是**在我们的界面里只按一个按钮**，
而不是系统不弹任何东西。系统那一层由 Android 强制，任何声称完全静默的实现都不可信。

---

## 二、权限总清单

按"能力 → 依赖"组织，便于判断删掉某项会影响什么。

### 2.1 基础通信与保活（安装即授予，无需用户操作）

| 权限 | 用途 | 缺失后果 |
|---|---|---|
| `INTERNET` / `ACCESS_NETWORK_STATE` / `ACCESS_WIFI_STATE` | 与服务端通信、判网络可用性 | 无法通信 |
| `RECEIVE_BOOT_COMPLETED` | 开机自启守护服务 | 孩子重启后管控失效直到手动打开 App |
| `FOREGROUND_SERVICE` 及子类型 `DATA_SYNC` / `SPECIAL_USE` | 常驻守护（心跳、指令长轮询） | App 退到后台即断连，家长端显示离线 |
| `NFC`（`uses-feature` required=false） | NFC 碰一碰绑定 | 该绑定方式不可用，不影响其他方式 |
| `USE_FULL_SCREEN_INTENT` | 锁屏/拦截时的全屏提醒 | 提醒降级为普通通知 |

### 2.2 运行时危险权限（装机一次性申请；DO/PO 机型可静默授予）

| 权限 | 对应功能 | 缺失后果 | 装机获取方式 |
|---|---|---|---|
| `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` | 位置上报、地理围栏 | 家长看不到孩子位置、围栏不告警 | DO 静默；否则系统弹窗（同一权限组合并弹一次） |
| `CAMERA` | 远程拍照（看看孩子周围） | 远程拍照失败 | 同上 |
| `RECORD_AUDIO` | 远程听音（环境音） | 远程听音失败 | 同上 |
| `READ/WRITE_EXTERNAL_STORAGE`（maxSdk=32） | 旧版截图落盘 | API 33+ 已由分区存储取代，无影响 | 按 API 版本自动跳过 |
| `POST_NOTIFICATIONS`（API 33+） | 守护通知、**屏幕采集授权的通知引导** | 收不到授权引导 → 实时看屏永远停在"连接中" | 同上 |

> 相机与麦克风从"用到再申请"改为"装机一并申请"：这是消灭二次授权的关键一步。
> 过去家长第一次点"远程拍照"时，孩子那侧才弹出相机权限框——场景已经失真了。

### 2.3 AppOps 特殊权限与无障碍（**App 与 DO 都无法代开**，必须用户在系统设置页亲手拨开关）

| 权限 | 对应功能 | 缺失后果（均为**静默失效**，最难排查） |
|---|---|---|
| `PACKAGE_USAGE_STATS`（使用情况访问） | 应用使用时长、单应用限额、黑名单事后拦截 | 时长恒为 0、限额设了不生效，界面无任何报错 |
| `SYSTEM_ALERT_WINDOW`（悬浮窗） | 全局护眼水印 | 水印不显示，家长以为开了其实没有 |
| `REQUEST_INSTALL_PACKAGES`（安装未知应用） | 家长端远程推送安装应用 | DO 机型不需要（走静默安装）；非 DO 时远程安装失败 |
| 无障碍服务 `OperationGuardAccessibilityService` | **密码闸门的系统级拦截**、应用启动拦截 | 孩子可从系统设置绕过密码、停用管控；应用管控形同摆设 |

### 2.4 屏幕采集（MediaProjection）

| 项 | 说明 |
|---|---|
| `FOREGROUND_SERVICE_MEDIA_PROJECTION` / `MICROPHONE` / `CAMERA` | Android 14+ 要求使用 mediaProjection 前台服务显式声明类型 |
| MediaProjection 用户确认 | **隐私红线**：必须用户点一次「立即开始」；令牌只在进程内存活，进程或设备重启后失效，届时会再由通知引导一次复权 —— 属 Android 强制机制，不计入二次授权 |
| 对应功能 | 实时看屏、远程截屏、远程录屏 |

### 2.5 设备身份（决定有多少能力可用）

| 身份 | 覆盖能力 | 获取方式 |
|---|---|---|
| **设备管理员（DA）** | 锁屏、禁用相机、密码策略、防卸载基础项 —— **主能力的基石** | 系统确认页点「激活」（装机流水线自动带过去） |
| **设备所有者（DO）/ 工作资料属主（PO）** | 静默安装、系统隐藏/挂起应用、Kiosk 锁定、USB 限制、全量静默授权、防恢复出厂 | **App 无法自提**：需 adb 命令或全新机二维码预置 |
| DO 的定位调整 | 本项目已把 DO 降级为**可选增强** | DA 已覆盖主能力，不再给家长增加恢复出厂的负担 |

## 三、一次性授权流水线（改造后的实现）

**入口位置**：登录成功之后、扫码绑定**之前**（因为扫码需要相机，授权在后会让一次授权的承诺当场作废）。

```
家长点「同意并授权」  ← 全 App 唯一一次需要家长做决定的点击
        │
        ▼  唯一的推进器 advance() 依次处理
  ① 设备管理员        → 系统确认页点「激活」，返回自动复检
  ② 运行时权限        → DO 机型静默授予；否则一次性系统弹窗，按权限组合并
  ③ 设置页项          → 使用情况访问 → 悬浮窗 → 安装未知应用 → 无障碍服务
                        自动依次跳过去，回来立刻复检并接下一项
  ④ 屏幕采集          → MediaProjection 系统弹窗点「立即开始」
        │
        ▼  全部就绪
  写入 AuthRepository.consentVersion = 1 → 自动分流到扫码绑定 → 主页
```

**关键设计（可直接对应到代码）**：

| 文件 | 职责 |
|---|---|
| `consent/OneTimeConsentViewModel.kt` | 唯一的流水线推进器；`advance()` 负责"下一个该办什么"，`retryCurrent()` 是清单按钮的统一动作 |
| `consent/OneTimeConsentScreen.kt` | 一整张清单 + 一个按钮；从系统页返回由 `Lifecycle ON_RESUME` 自动复检 |
| `consent/ConsentItem.kt` | 把四种获取方式（运行时 / 管理员 / 设置页 / 录屏）抽象成同一种模型，UI 无分支 |
| `permission/SpecialPermission.kt` | 定义必须手动开启的项，新增 `ACCESSIBILITY`（无障碍）并取消"必做/可选"二分 |
| `permission/PermissionGranter.kt` | 静默授予 + 加固基线 + 协议留痕；权限清单只有一份 |
| `permission/DeviceAdminRequest.kt` | 设备管理员意图的唯一构造处（历史上两处不一致曾导致"点了没反应"） |
| `core/data/.../AuthRepository.kt` | `consentVersion` 版本化记账——清单变长时存量设备自动补一次，幂等且不打扰已就绪项 |

**防悬挂设计**：
1. 只有"上一趟确实开通了"才自动打开下一项；否则停在清单页让家长决定 —— 避免在 ROM 不允许开启的机型上无限循环；
2. 始终提供「剩余项不再授权，直接进入」出口 —— 避免家长被永久卡在装机页；
3. 每类系统交互只自动发起一次 —— 家长明确拒绝后不再纠缠。

## 四、位置采集与后台限制（2026-10-07 已落地）

### 问题
`GuardService` 以前台服务 `dataSync|specialUse` 常驻，家长的"立即定位"指令在其中执行，
即**绝大多数时候 App 不在前台**。而 Android 10(API 29)+ 起，没有 `ACCESS_BACKGROUND_LOCATION`
的 App 在后台读取位置会被系统直接拒绝（`getLastKnownLocation` 抛异常或返回 null）。
结果就是：家长端几乎永远看不到位置，回执却只写"未授权定位权限或设备当前无任何位置缓存"，
把排查方向彻底带偏。

### 为什么不直接补后台位置权限
1. `ACCESS_BACKGROUND_LOCATION` 是 Google Play 受限权限，需专项申报；
2. **Play 家庭政策明确禁止面向儿童的 App 申请后台位置权限** —— 本项目正是孩子端。
因此"申请后台位置 + location 类型前台服务"这条补救路径在合规上不可行。

### 采用的方案：后台不读 + 前台自动补传
- `LocationCollector.collectAndUpload()`：后台先查 `AppForeground.isForeground`，
  不在前台就**不调用 LocationManager**（调用必定失败，还可能抛异常），
  改为登记待办并返回 `LocationFailure.BACKGROUND_RESTRICTED`；
- `AppForeground` 新增前台订阅（resumed 计数 **0→1** 的边沿触发，App 内页面互跳不重复），
  `LocationCollector` 注册后在上述时刻自动补传上一次被搁置的定位；
- `GuardService` 回执改为按 `LocationFailure.hint` 输出**准确原因**，
  家长会看到"孩子此刻未使用平板……孩子打开平板后会自动补传"，而不是含糊的失败；
- 每个 provider 的 `getLastKnownLocation` 逐个 `runCatching`，避免 ROM 差异让整条链路断掉；
- Manifest 的定位权限处加了注释，明确说明**不要**补 `ACCESS_BACKGROUND_LOCATION`
  或给服务加 `location` 前台服务类型（防止后人顺手"修好"导致上架被拒）。

**家长侧实际体验**：孩子正在用平板时下发定位 → 立即上报；孩子没在用 → 回执说明会补传，
孩子下次打开 App 的瞬间自动把位置补上去。
